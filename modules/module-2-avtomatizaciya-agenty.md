# Модуль 2. Автоматизация и агенты

**Поток**: Практик / Инженер | **Длительность**: 4 занятия по 90 мин | **Пререквизиты**: Модуль 1

## Цели модуля

Студент понимает, как расширять возможности Claude через MCP-серверы, строить
регулярные автоматические задачи и многоагентные пайплайны, а также осознанно
управлять контекстом длинных сессий.

---

## Занятие 1: MCP — протокол расширения возможностей

- Проблема: у модели по умолчанию нет доступа к внешним системам — MCP это решает
- Архитектура: MCP-сервер предоставляет инструменты/ресурсы, Claude их вызывает
- Обзор готовых серверов: браузер, файловая система, сторонние интеграции
- Подключение существующего MCP-сервера к проекту, проверка через ToolSearch

**Практика**: подключить один готовый MCP-сервер (например, браузер) и выполнить
задачу, требующую его инструментов.

## Занятие 2: Написание собственного MCP-сервера

- Минимальный сервер: один инструмент, чёткая схема входа/выхода
- Инструкции для агента (server instructions) — как объяснить модели, когда и как
  вызывать инструмент
- Тестирование сервера в изоляции перед подключением

**Практика**: написать простой MCP-сервер (например, обёртку над внутренним API
или локальной базой) с одним-двумя инструментами.

## Занятие 3: Регулярные задачи и повторяющиеся сценарии

- Scheduled tasks / cron-агенты: разница между разовым запуском и регулярным
- `/loop`: самотемповые повторяющиеся задачи, когда предпочесть его cron-у
- Практические паттерны: мониторинг источника данных, регулярная сводка, алерты
- Важно: сначала проговорить с пользователем/командой, какие данные и куда уходят —
  автоматизация с выходом во внешние системы требует явного согласия на отправку

**Практика**: спроектировать (без обязательного реального запуска) регулярную задачу
для рабочего сценария студента — что проверяется, с какой частотой, что делать при
ошибке.

## Занятие 4: Многоагентные workflow и управление контекстом

- pipeline() — независимый проход каждого элемента через все стадии, барьер не нужен
- parallel() — барьер, когда он оправдан (дедупликация, ранний выход при нулевом
  результате), а когда это просто лишнее ожидание
- Паттерны качества: адверсариальная проверка (несколько скептиков опровергают
  находку), панель судей, разнообразные «линзы» проверки
- Управление контекстом: автосжатие истории, что теряется и как этого избежать
  (явные заметки, промежуточные файлы, память)
- Персистентность между сессиями: чем память отличается от контекста одного чата

**Практика**: описать (спроектировать) workflow для задачи «проверить N файлов на
одну и ту же проблему и подтвердить находки независимо» — какие стадии, где нужен
барьер, где нет.

---

## Итоговый проект модуля

Спроектировать и (если позволяет доступ) реализовать одного агента, который:
1. Регулярно проверяет источник данных или состояние системы
2. Обрабатывает результат (анализ/фильтрация)
3. Формирует отчёт и решает, требует ли результат уведомления
4. Обрабатывает ошибки: что происходит, если источник недоступен

## Критерии проверки

- [ ] Студент может объяснить разницу между MCP-сервером и обычным инструментом
- [ ] В проекте предусмотрена обработка ошибки/недоступности источника
- [ ] Студент понимает, когда использовать pipeline, а когда parallel с барьером
- [ ] Автоматизация не отправляет данные во внешние системы без явного шага подтверждения
