Всё, что вы построили в модулях 1–8, работает ровно до вопроса «откуда вы знаете, что это правильно?». Финальный модуль «Инженер» не даёт новых инструментов — даёт дисциплину: проверять ИИ так же строго, как нового сотрудника, и не дать одному агенту испортить работу другого. Без этого проекты нельзя выпускать за пределы ноутбука.

## Правдоподобно — не значит правильно

Главная ловушка — путать уверенный тон ответа с корректностью: модель одинаково гладко формулирует и верный расчёт, и ошибку в нём. Беглое чтение оценивает синтаксис, а не то, обработан ли пустой массив или отрицательное число. Значит, результат ИИ нельзя принимать по ощущению «выглядит разумно» — нужен внешний критерий: тест, который либо проходит, либо нет.

- Что именно проверялось — реальные сценарии или один удобный пример?
- Есть ли непроверенные граничные случаи (пустой ввод, дубликаты, чужой часовой пояс, чужая локаль — региональные настройки формата даты, разделителя дробей и т.п.)?
- Может ли кто-то, кроме автора решения, независимо подтвердить результат?

**Практика.** Возьмите ответ ИИ, которому вы поверили «на глаз», сформулируйте три граничных случая, способных его сломать, прогоните их и зафиксируйте расхождение.

## Автоматические наборы проверок: eval suite

Проверка «на глаз» не масштабируется: при следующем изменении никто не вспомнит, что перепроверять руками. Решение — eval suite: набор реальных кейсов с ожидаемым результатом, прогоняемый автоматически и выдающий отчёт «прошло / не прошло». Хороший набор строится не из абстрактных юнит-тестов, а из реальных случаев — в идеале из продакшна или жалоб пользователей. На практике такой прогон делают инструменты вроде [promptfoo](https://www.promptfoo.dev/) — открытого фреймворка для eval suite LLM-приложений. Ниже — иллюстративный пример формата отчёта, а не вывод конкретной команды:

```text
Кейсов: 40 · Прошло: 34 · Провал: 6
Класс ошибки: неверная обработка часовых поясов (5 из 6)
```

Это полезнее, чем «40 из 40 зелёные» с плохим покрытием: отчёт указывает не только что сломалось, но и почему. Здесь не шесть разрозненных багов, а один системный пробел — группировка по первопричине превращает красные строки в план действий: чинить один механизм, а не шесть симптомов.

**Практика.** Соберите 15–20 реальных кейсов для одной задачи проекта, зафиксируйте вход и ожидаемый результат, прогоните через текущее решение и составьте отчёт «кейсов / прошло / провал / класс ошибки».

## Почему самопроверке ИИ нельзя доверять вслепую

Соблазн — попросить тот же ИИ проверить свою работу. Изъян: модель повторяет предположения и слепые пятна, что привели к ошибке, — ловит опечатки, но не саму неверную интерпретацию задачи, ведь она использовалась при генерации.

Рабочий паттерн — независимая проверка: второй агент (или новый заход без доступа к рассуждениям первого), задача которого не согласиться, а опровергнуть результат. В Claude Code это можно сделать через отдельный subagent: он получает только результат первого агента, без его хода рассуждений, и ищет в нём ошибку.

- «Оцени свою работу» почти всегда возвращает «выглядит хорошо».
- «Найди причину, почему это может быть неверным» вынуждает искать контрпримеры.

Панель из нескольких проверяющих снижает риск общей слепой зоны, но не заменяет проверку человеком при высокой цене ошибки.

**Практика.** Возьмите результат, прошедший самопроверку агента, и попросите независимого агента найти способ, которым он может быть неверным.

## Проверки безопасности при каждом изменении

Частая ошибка даже опытных команд — откладывать проверку безопасности «на потом», перед релизом. К этому моменту десятки мелких изменений, каждое безобидное отдельно, вместе создают незапланированную дыру.

Правильная модель — сканирование уязвимостей при каждом изменении: перед коммитом, слиянием, публикацией. Это часть процесса, как линтер или тесты, а не отдельный ручной запуск. На практике это делают сканеры вроде [gitleaks](https://github.com/gitleaks/gitleaks) (поиск секретов) или [semgrep](https://semgrep.dev/) (поиск уязвимых паттернов кода), запущенные автоматически. В Claude Code это оформляется как hook в `.claude/settings.json` — сканер срабатывает сам при каждом коммите, без ручного напоминания. Безопасность — свойство процесса разработки, а не финальный аудит.

**Практика.** Включите проверку безопасности в тот же workflow, где уже прогоняются тесты вашего последнего изменения — так, чтобы её нельзя было случайно пропустить, только осознанно отключить.

## Безопасность многоагентных систем простыми словами

Как только над задачей работает несколько агентов — конвейером, параллельно, с общей памятью — появляется класс рисков, которого нет у одного агента в изоляции.

- **Один агент портит общую память.** Несколько агентов читают и пишут в общий файл состояния — ошибка или галлюцинация одного становится «фактом» для остальных, они доверяют записи, не перепроверяя её. Неверный вывод на раннем шаге незаметно становится исходными данными для всех следующих.
- **Опасность на стыке безопасных по отдельности инструментов.** «Читать входящие письма» безопасен сам по себе, «выполнять команды в терминале» — тоже. Но агент с доступом к обоим создаёт путь, которого не было ни у одного отдельно: текст из письма интерпретируется как команда. Риск в сочетании, поэтому доступ агента нужно оценивать целиком.
- **Заражённая инструкция передаётся между агентами.** Разновидность prompt injection (внедрение вредоносной инструкции через чужой текст): Agent A обрабатывает недоверенный контент и передаёт результат Agent B как обычное сообщение — без пометки «это данные, а не инструкции». Agent B может исполнить спрятанное в контенте, потому что агенты по умолчанию доверяют друг другу. Цепочка «источник → агент 1 → агент 2» — испорченный телефон, только сообщение здесь исполняемо.

Вывод одинаков для всех трёх: систему нельзя проектировать по агентам отдельно — только целиком: память, связки инструментов, точки входа недоверенного текста.

**Практика.** Нарисуйте схему многоагентного пайплайна: что каждый агент читает, какие инструменты вызывает, куда пишет результат. Отметьте точку входа недоверенного текста и её путь до самого рискованного инструмента.

## Секреты не должны жить в коде — и не должны быть видны агенту

API-ключи, пароли, токены доступа (не путать с токенами контекста из Модуля 2.5) не должны храниться в файлах проекта, попадать в промпт или быть видны агенту. Дело не только в утечке через git: секрет в тексте, который читает модель, может быть процитирован в ответе, логе или сообщении другому агенту.

Рабочий принцип — секрет передаётся через отдельный непрозрачный для модели канал:

- **переменные окружения** — значения, заданные вне кода на уровне операционной системы или процесса (например, файл `.env`), которые код читает по имени, не храня секрет в тексте программы;
- **менеджер секретов** — сервис вроде AWS Secrets Manager или HashiCorp Vault, который хранит секрет и выдаёт его по запросу вызывающему сервису;
- **брокер учётных данных** — промежуточный сервис, который сам предъявляет секрет внешней системе от имени агента, не передавая значение агенту вовсе.

Агенту достаточно знать, что секрет существует, — не его содержимое. Это относится и к `CLAUDE.md`/настройкам проекта: сам файл должен ссылаться на переменную окружения, а не содержать значение секрета.

**Практика.** Проверьте реальный проект: есть ли в коде, в `CLAUDE.md`, в истории промптов открытый секрет? Перенесите его в переменные окружения: создайте файл `.env`, добавьте туда строку вида `ANTHROPIC_API_KEY=...`, добавьте `.env` в `.gitignore`, а в коде читайте значение через `os.environ` (Python) или `process.env` (Node.js) — и убедитесь, что агент справляется с задачей, не видя самого значения.

## Итоговый проект модуля

Финальный проект — две обязательные части, иначе проверка качества остаётся теоретической. К части 1 обязательно прилагаются три результата из практик по ходу модуля — независимая проверка, схема многоагентного пайплайна (или пояснение, почему в проекте один агент) и аудит секретов; без них чек-лист ниже не закрыть.

1. **Соберите eval suite для своего проекта.** Минимум 20 реальных кейсов, автоматический прогон, отчёт «кейсов / прошло / провал / класс ошибки» по первопричине. Добавьте проверку безопасности в тот же процесс. Приложите: (а) результат независимой проверки хотя бы одного кейса вторым агентом; (б) схему многоагентного пайплайна проекта с точкой входа недоверенного текста — или пояснение, что в проекте один агент; (в) аудит секретов проекта (код, `CLAUDE.md`, история промптов) и подтверждение, что открытых секретов не осталось.
2. **Разберите публичный постмортем из индустрии.** Постмортем (от англ. *post-mortem* — «после случившегося») — публичный разбор инцидента (сбой, утечка данных, prompt injection, ошибка автоматизации), который компания сама публикует в своём блоге или на статус-странице после случившегося. Несколько реальных примеров для старта:
   - [Статус Claude — история инцидентов](https://status.claude.com/history)
   - [Статус OpenAI — история инцидентов](https://status.openai.com/history)
   - [Cloudflare — разбор сбоя 2 июля 2019](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/)

   Также подойдёт любой материал, найденный по словам «postmortem» или «incident report» в блоге технологической компании. Ответьте письменно: что не поймали существующие проверки; это провал одного правила или пересечение нескольких решений; какая проверка предотвратила бы инцидент.

## Чек-лист перед сдачей

- [ ] В eval suite минимум 20 кейсов из реальных сценариев, а не один удобный пример
- [ ] Отчёт группирует провалы по первопричине, а не перечисляет номера тестов
- [ ] Хотя бы один результат проверен независимо от автора
- [ ] Проверка безопасности встроена в процесс изменений, а не откладывается «на потом»
- [ ] Для многоагентной части описано, что происходит с общей памятью и какие инструменты в одной связке
- [ ] В коде, конфигурации и истории промптов нет открытых секретов
- [ ] Разбор постмортема указывает на конкретную проверку, которая предотвратила бы инцидент
