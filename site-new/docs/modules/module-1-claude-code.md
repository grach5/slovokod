**Поток**: Практик / Инженер · **Длительность**: 5 занятий по 90 минут · **Пререквизиты**: Модуль 0 (основы промптинга), базовые навыки терминала и git

Claude Code — это CLI-агент, который читает, редактирует и запускает код в вашем проекте по запросу на естественном языке. Модуль строится вокруг одного тезиса: Claude Code не заменяет разработчика, а меняет то, на что уходит его время — рутина навигации, черновой правки, тестов и оформления PR делегируется агенту, а разработчик управляет процессом и принимает архитектурные решения. К концу модуля вы пройдёте полный цикл: от установки инструмента до реального PR в open-source репозитории с тестом и код-ревью.

## Занятие 1. Установка, первый запуск, структура проекта

### Установка и вход

Claude Code устанавливается как обычный CLI-пакет (`npm install -g @anthropic-ai/claude-code` на момент написания курса — точная команда всегда актуальна в официальной документации, см. раздел «Ресурсы»). После установки — вход в аккаунт и выбор модели по умолчанию: по тому же принципу цена/качество/скорость из Модуля 0 — быстрая и дешёвая модель для навигации и мелких правок, старшая — для архитектурных решений и сложного рефакторинга.

### CLAUDE.md: память проекта, а не описание проекта

`CLAUDE.md` — файл в корне репозитория, который агент читает в начале каждой сессии. Частая ошибка новичков — превращать его в копию README: описывать архитектуру, историю проекта, список фич. Агент это и так вычитает из кода за несколько секунд поиска. Ценность `CLAUDE.md` — в том, что **нельзя** быстро вывести из кода: команды, соглашения, ограничения, о которых иначе агент узнаёт только методом проб и ошибок.

Пример рабочего `CLAUDE.md` для типичного Node/TypeScript-проекта:

```markdown
# CLAUDE.md

## Команды
- Установка: `npm ci` (не `npm install` — используем lock-файл)
- Тесты: `npm run test`, e2e: `npm run test:e2e` (нужен запущенный dev-сервер)
- Линт: `npm run lint:fix`, сборка: `npm run build`

## Соглашения
- Стиль: Prettier + ESLint, конфиги в репозитории — не переопределять вручную
- Коммиты: Conventional Commits (`fix:`, `feat:`, `refactor:`)

## Особенности проекта
- `src/legacy/` — код на поддержке, новые фичи туда не добавлять
- Переменные окружения — в `.env.example`, реальные значения — только через 1Password
- `src/billing/` — критичная логика биллинга, изменения проходят ревью отдельно
```

Обратите внимание, чего здесь нет: не описано, что делает каждый модуль, не пересказана структура папок — это агент прочитает сам через Glob/Grep за секунды. `CLAUDE.md` фиксирует то, что иначе теряется: «`npm install` не используем», «биллинг трогать осторожно», «легаси-код не трогать».

### Режимы разрешений

Claude Code работает в режиме подтверждения каждого действия (безопасно, но медленно) или auto-accept для определённых категорий (быстрее, но требует доверия к правилам). На новом проекте — подтверждение каждого шага, пока не сложится понимание предсказуемости агента. На знакомом проекте с настроенным `.claude/settings.json` (занятие 5) — auto-accept для чтения и тестов, подтверждение — для push, удаления файлов, правок вне рабочей директории. Граница проходит не по сложности действия, а по его обратимости.

### Структура типичной сессии

Любая содержательная задача проходит четыре фазы: **запрос** (формулировка с достаточным контекстом — см. Модуль 0), **план** (для нетривиальных задач агент намечает шаги до правки кода — пропуск этой фазы на сложных задачах частая причина того, что агент «уезжает не туда»), **выполнение** (чтение/правка/запуск команд) и **проверка** (тесты, линт, просмотр диффа перед коммитом). Разница между простой и сложной задачей — не в объёме кода, а в числе развилок: «исправь опечатку в строке 42» решения не требует, а «перевести хранение сессий на другое хранилище» содержит их несколько (миграция данных, откат при сбое, тестирование), и здесь пропуск плана означает, что агент выбирает первую попавшуюся развилку, а не обязательно нужную вам.

### Практика

Установите Claude Code в тестовом (не боевом) репозитории. Напишите `CLAUDE.md` по образцу выше: реальные команды сборки и тестов этого репозитория, реальные соглашения о стиле, если они есть. Проверьте гипотезу на практике — попросите агента запустить тесты без указания команды и с `CLAUDE.md`, содержащим команду; сравните, сколько итераций понадобилось агенту, чтобы понять, как устроен проект.

## Занятие 2. Навигация и чтение кода

### Read, Glob, Grep — три разных вопроса

Начинающие путают эти три инструмента, потому что все они «про поиск», но отвечают на разные вопросы:

- **Read** — «покажи мне этот конкретный файл» (путь уже известен).
- **Glob** — «какие файлы существуют по такому паттерну имени» (например, `src/**/*.test.ts` — найти все тестовые файлы).
- **Grep** — «в каком файле встречается такая строка или паттерн» (например, `handleLogin` — найти, где определена функция).

Практическое правило: если вы знаете имя файла — Read. Если знаете часть имени или расширение, но не знаете, где файл лежит — Glob. Если не знаете ни имени, ни расположения, но знаете, что ищете по содержимому (название функции, текст ошибки, TODO-комментарий) — Grep. Частая ошибка — просить агента «открой файл авторизации», не уточнив, что на самом деле это Grep-задача («найди, где реализована функция логина»), а не Read по угаданному имени.

### Разведка большого проекта без ручного чтения

Заказать «объясни архитектуру» без уточнений — плохой промпт: агент либо прочитает случайные 10 файлов, либо начнёт с README и остановится. Более эффективный запрос указывает точку входа и глубину:

> «Начни с `src/index.ts`, проследи, как обрабатывается HTTP-запрос от роута до записи в БД. Не читай тесты и конфиги — только код в `src/`. Дай карту: файл → что делает → что вызывает дальше.»

Это превращает открытую задачу в управляемый обход графа зависимостей — агент не должен читать «всё», ему нужно пройти по одному конкретному пути.

### Explore-агент для разведки

Для задач вида «разберись, где что лежит, прежде чем что-то менять» есть смысл делегировать разведку read-only агенту (Explore), а не выполнять её в основной сессии. Причина не в скорости, а в чистоте контекста: разведка включает чтение десятков файлов, большая часть которых не пригодится, и если она идёт в основной сессии — этот «шум» остаётся в контексте и мешает точности на следующих шагах. Explore возвращает уже сжатую сводку, а не сырые прочитанные файлы.

Правило: задача явно read-only → отдать Explore. Проект большой и незнакомый, путь к нужному коду неочевиден → отдать Explore, дать сводку. Файл, который нужно менять, уже известен по имени и расположению → не делегировать, читайте сами — это лишний шаг.

### Практика

Возьмите открытый репозиторий среднего размера (например, небольшой веб-фреймворк или CLI-утилиту с открытым кодом). Сформулируйте задачу «найди, где обрабатывается авторизация пользователя» и попросите агента составить карту потока данных: точка входа → middleware/декоратор проверки → где выдаётся токен → где токен валидируется на последующих запросах. Зафиксируйте результат в виде короткого markdown-списка файлов с однострочным описанием роли каждого.

## Занятие 3. Редактирование, тесты, отладка

### Edit vs Write

**Edit** делает точечную замену: находит конкретный фрагмент текста в файле и заменяет его на новый, оставляя всё остальное нетронутым. **Write** перезаписывает файл целиком. Правило простое: если меняется часть файла — Edit; Write оправдан только для новых файлов или полной, осознанной перезаписи. Использовать Write для правки существующего файла рискованно: агент может непреднамеренно потерять код, не упомянутый явно в задаче.

### Правило маленьких диффов

Одна из самых недооценённых практик: просить агента решать «одну проблему за раз», а не пакетом. Разница на практике:

**Плохой промпт (пакетная правка, большой дифф):**
> «Почини баг с валидацией email, заодно отрефактори весь модуль форм и добавь TypeScript-типы там, где их нет.»

Результат — дифф на 300+ строк, где реальный фикс бага теряется среди рефакторинга и типизации, и ревьюеру почти невозможно оценить, исправлен ли именно баг, а не задет побочный эффект рефакторинга.

**Хороший промпт (одна проблема, маленький дифф):**
> «Есть баг: `validateEmail()` в `src/forms/validation.ts` принимает `user@domain` без TLD как валидный email. Исправь только это, не трогай остальные функции файла.»

Пример конкретного до/после:

```diff
--- a/src/forms/validation.ts
+++ b/src/forms/validation.ts
@@ -12,7 +12,7 @@ export function validateEmail(value: string): boolean {
   if (!value) return false;
-  const pattern = /^[^\s@]+@[^\s@]+$/;
+  const pattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
   return pattern.test(value);
 }
```

Пять изменённых символов вместо трёхсот строк. Такой дифф ревьюер прочитает за 10 секунд. Рефакторинг и типизацию стоит вынести в отдельные последующие задачи — не потому что они не нужны, а потому что смешивание разных по сути изменений в одном коммите усложняет откат, если что-то одно из них окажется неверным.

### Генерация тестов под существующий код

Просьба «напиши тесты для этой функции» без уточнений часто даёт тесты, которые просто повторяют реализацию (assert того, что функция делает, а не того, что она должна делать). Более полезный запрос указывает, что важно проверить:

> «Напиши тесты для `validateEmail()`: граничные случаи — пустая строка, отсутствие `@`, отсутствие домена верхнего уровня, несколько `@`, юникод в локальной части. Используй `describe`/`it`, как в остальных тестах проекта.»

### Интерпретация падающих тестов

Красный тест — источник конкретной информации, а не просто сигнал «почини». Сообщение о падении обычно содержит `expected` (что тест ждал), `received` (что получилось на самом деле) и стек вызовов. Частая ошибка — сразу лезть в стек, пропуская `expected`/`received`, из-за чего фикс адресует не ту причину. Иногда падение означает, что не прав тест, а не код: например, если ожидание устарело после легитимного изменения поведения — тогда чинить нужно тест, а не код.

### Итеративная отладка

Рабочий цикл отладки — не «исправь баг», а последовательность из четырёх шагов, и пропуск любого из них снижает надёжность результата:

1. **Воспроизвести** — написать минимальный сценарий, который стабильно вызывает баг.
2. **Локализовать** — сузить до конкретной функции/строки через логи, бисекцию или чтение стека вызовов.
3. **Исправить** — минимальное изменение, устраняющее причину, а не симптом.
4. **Проверить** — прогнать тест, который воспроизводил баг, убедиться, что он теперь проходит, и что остальные тесты не сломались.

Пример: баг-репорт гласит «после обновления профиля счётчик уведомлений не сбрасывается».

> Вы: «После `PATCH /profile` поле `unreadCount` не обнуляется. Воспроизведи через тестовый клиент API, напиши падающий тест в `tests/profile.test.ts`, затем найди причину в `src/profile/handler.ts` — не исправляй, пока тест не будет стабильно падать.»

Агент воспроизводит: тест делает `PATCH /profile`, затем проверяет `GET /notifications/count` — падает, `unreadCount` остаётся 5 вместо 0. Локализует: `updateProfile()` не вызывает `resetNotifications()`, хотя эта функция уже существует и вызывается из `markAsRead()`. Исправляет точечным диффом:

```diff
--- a/src/profile/handler.ts
+++ b/src/profile/handler.ts
@@ -24,6 +24,7 @@ export async function updateProfile(req: Request, res: Response) {
   const updated = await db.profiles.update(userId, req.body);
+  await resetNotifications(userId);
   res.json(updated);
 }
```

> Проверка: падавший тест теперь зелёный, остальной набор тестов — без регрессий.

### Практика

Возьмите баг-репорт (реальный из issue-трекера open-source проекта или сформулированный самостоятельно). Пройдите весь цикл: воспроизведите баг, напишите падающий тест, зафиксируйте, что он действительно красный по правильной причине (а не из-за опечатки в самом тесте), исправьте минимальным диффом, убедитесь что тест позеленел и ничего не сломалось.

## Занятие 4. Git, ревью, subagents

### Коммиты через Claude Code

Агент умеет сам формировать сообщение коммита на основе диффа, но качество зависит от того, снабжён ли он контекстом «почему», а не только «что» — дифф и так виден в `git diff`. Что **не** коммитить: не только `.env` и секреты, но и временные логи/дампы отладки, закомментированный «на всякий случай» старый код, случайно захваченные посторонние изменения форматирования — их стоит откатить отдельно от содержательного изменения.

### `/code-review`

Команда ревью работает на нескольких уровнях глубины — от быстрой проверки очевидных проблем (`low`) до многоступенчатого разбора архитектурных последствий (`ultra`). Для маленького точечного фикса достаточно `medium`; `ultra` стоит придерживать для рискованных изменений (миграции данных, биллинг, публичный API), где отдача оправдывает более дорогую и медленную проверку.

Результат ревью — не «одобрено/отклонено» одним словом, а инлайн-комментарии к конкретным строкам: где риск, где несоответствие соглашениям проекта, где отсутствует обработка ошибки. Ревью, которое не находит вообще ничего, — повод присмотреться внимательнее, а не повод для радости: скорее всего, проверка была слишком поверхностной для уровня риска задачи.

### Создание PR: пример описания

Хорошее описание PR отвечает на три вопроса — что изменилось, почему, как это проверено. Пример для бага из занятия 3:

```markdown
## Что

Счётчик непрочитанных уведомлений (`unreadCount`) не сбрасывался после
обновления профиля пользователя через `PATCH /profile`.

## Почему

`updateProfile()` в `src/profile/handler.ts` не вызывал `resetNotifications()`,
хотя эта логика уже использовалась в `markAsRead()`. Обработчик профиля был
добавлен позже, и про существующий сброс счётчика просто забыли.

## Изменения

- `src/profile/handler.ts`: добавлен вызов `resetNotifications(userId)`.
- `tests/profile.test.ts`: новый тест на баг (PATCH /profile → count = 0).

## План тестирования

- [x] Новый тест — падал до фикса, зелёный после
- [x] Полный набор тестов — без регрессий (`npm run test`)
- [x] Ручная проверка в dev-окружении: счётчик обнулился в UI
- [ ] Нужна проверка на staging перед мерджем
```

Такое описание позволяет ревьюеру-человеку понять контекст без чтения кода и решить, нужно ли смотреть дифф подробно.

### Subagents: когда делегировать, а когда — нет

В Claude Code есть несколько специализированных типов агентов: **Explore** (только чтение, для разведки — занятие 2), **Plan** (архитектурное планирование до начала кода) и **general-purpose** (полноценный агент со всеми инструментами, для комплексных многошаговых задач). Критерий делегирования — не «сложность» сама по себе, а **независимость и объём побочного контекста**:

**Делегировать стоит:** «Проверь все файлы в `src/api/`, найди эндпоинты без валидации входных параметров, дай список файл:строка» — read-only разведка с большим объёмом промежуточного шума (десятки просмотренных файлов), результат которой — короткий список. Кандидат для Explore или general-purpose в фоне.

**Делать самому стоит:** «Исправь опечатку в сообщении об ошибке в `src/errors.ts`, строка 42» — одношаговая задача с уже известным местоположением; делегирование здесь добавляет накладные расходы без выгоды.

Правило одной фразой: делегируйте, когда задача объёмна и независима либо генерирует много «шумного» промежуточного контекста. Не делегируйте тривиальные, одношаговые, уже локализованные правки.

Отдельно про Plan: он оправдан, когда неверно выбранный подход дорого откатывать — например, «перевести хранение сессий с in-memory на Redis» затрагивает несколько слоёв (middleware, деплой, откат при сбое), и стоит сначала разложить подход на шаги. А для «добавить недостающее поле в DTO» отдельное планирование избыточно — план окажется длиннее самого изменения.

### Изоляция через worktree

Когда несколько агентов должны параллельно работать над разными частями задачи, не мешая друг другу, используется git worktree — отдельная директория с тем же репозиторием на другой ветке: один агент чинит баг в `worktree-fix`, второй параллельно пишет документацию в `worktree-docs`, не создавая конфликтов в файловой системе.

### Практика

Возьмите баг, исправленный в занятии 3. Прогоните `/code-review` на уровне минимум `medium`, разберите каждый инлайн-комментарий (согласиться и исправить, либо аргументированно отклонить). Оформите PR по образцу выше — с разделами «Что / Почему / Изменения / План тестирования».

## Занятие 5. Workflows и настройка поведения

### Когда одного агента недостаточно

Есть класс задач, которые естественно распадаются на независимые подзадачи: ревью одного диффа по нескольким несвязанным критериям, обработка списка из десяти похожих, но независимых файлов, сбор информации из нескольких независимых источников. В таких случаях фан-аут на несколько агентов быстрее и чище одного агента, обрабатывающего всё последовательно в одном раздувающемся контексте.

### pipeline() vs parallel()

**parallel()** — независимые задачи запускаются одновременно, ни одна не зависит от результата другой; барьер (точка ожидания всех результатов) нужен только в конце, перед агрегацией. **pipeline()** — задачи выполняются последовательно, каждый следующий шаг использует результат предыдущего; конкурентность здесь не нужна и невозможна по своей природе.

**Пример parallel:** дифф на 200 строк нужно проверить по трём независимым критериям — безопасность, производительность, соответствие стилю. Три агента запускаются одновременно, каждый читает один и тот же дифф под своим углом, барьер — дождаться всех трёх отчётов и свести их в один список замечаний.

**Пример pipeline:** «собери упоминания продукта из открытых источников, проверь достоверность каждого, сформируй итоговый отчёт» — шаг «собрать» должен завершиться до того, как начнётся «проверить», а «сформировать отчёт» не может начаться без проверенного списка. Распараллелить эти шаги не получится — они последовательно зависимы по данным, а не только по времени выполнения.

Правило: если шаг Б можно физически начать, не дожидаясь результата шага А — это parallel. Если шаг Б логически требует именно результат шага А — это pipeline, и попытка сделать вид, что это parallel, даст агента, работающего с неполными данными.

### `.claude/settings.json`

Файл конфигурации на уровне проекта задаёт разрешения, хуки и allowlist команд, которые не нужно подтверждать вручную каждый раз. Пример типичного `.claude/settings.json` для проекта из занятия 1:

```json
{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Bash(npm run lint:*)", "Bash(git status)", "Bash(git diff:*)"],
    "ask": ["Bash(git push:*)", "Bash(git commit:*)", "Bash(rm:*)"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          { "type": "command", "command": "npm run lint:fix -- $CLAUDE_FILE_PATH" }
        ]
      }
    ]
  }
}
```

Здесь read-only и низкорисковые команды в allowlist — их не нужно подтверждать каждый раз, команды с необратимыми последствиями (push, commit, rm) явно требуют подтверждения. Хук `PostToolUse` на событие `Edit` прогоняет линтер с автофиксом сразу после правки — ловит проблемы стиля до ревью. Кроме `PostToolUse` есть `PreToolUse` (блокирует опасное действие до выполнения) и `Stop` (финальная валидация при завершении сессии — например, прогнать полный набор тестов).

### Практика

Настройте allowlist для часто используемых read-only команд вашего тестового проекта (тесты, линт, статус git — как в примере выше). Опишите текстом сценарий из вашей практики, где оправдан workflow, а не единственный агент: какая задача, почему она распадается на независимые части, pipeline это или parallel и почему. Реальный запуск не обязателен — многоагентные workflow расходуют больше токенов, это стоит проговаривать команде заранее.

## Итоговый проект модуля

Возьмите реальный open-source репозиторий (или рабочий проект, если он подходит по масштабу) и пройдите полный цикл, объединяющий все пять занятий:

1. **Найдите баг** — через issue-трекер репозитория (метки вроде `good first issue` или `bug` — хороший ориентир) или через собственное тестирование функциональности.
2. **Настройте `CLAUDE.md`**, если в проекте его ещё нет — команды сборки, тестов, линта, ключевые соглашения.
3. **Воспроизведите баг** и напишите падающий тест, который его демонстрирует.
4. **Исправьте** минимальным, сфокусированным диффом — по правилу «одна проблема за раз» из занятия 3.
5. **Прогоните `/code-review`** минимум на уровне `medium`, разберите замечания.
6. **Оформите PR** с описанием по структуре «Что / Почему / Изменения / План тестирования».

### Чек-лист проверки

- [ ] `CLAUDE.md` содержит нужные команды и соглашения, но не дублирует то, что и так видно из кода
- [ ] Дифф маленький и сфокусирован на одной проблеме (нет посторонних правок стиля или рефакторинга «заодно»)
- [ ] Есть тест, который стабильно падал до исправления и стабильно проходит после
- [ ] Полный набор тестов проекта проходит без регрессий
- [ ] PR прошёл `/code-review` минимум на уровне `medium`, критичные замечания устранены
- [ ] Описание PR отвечает на три вопроса: что изменилось, почему, как проверено
- [ ] Вы можете объяснить своими словами, в каком случае в этой задаче стоило (или не стоило) делегировать часть работы subagent, и почему
