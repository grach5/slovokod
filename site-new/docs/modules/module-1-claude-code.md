Claude Code — CLI-агент: читает, редактирует и запускает код по запросу на естественном языке. Рутина уходит агенту, архитектура — за вами.

## Занятие 1. Установка, CLAUDE.md, режимы

**Установка**: нужен Node.js 18 или новее (проверить: `node -v` в терминале; нет — поставить с [nodejs.org](https://nodejs.org)). Дальше: `npm install -g @anthropic-ai/claude-code` (см. документацию). Модель по умолчанию: быстрая — для навигации, старшая — для архитектуры.

### CLAUDE.md — память проекта, а не README

Не пересказывайте архитектуру — агент прочитает её сам. Фиксируйте то, что не видно из кода: команды, соглашения, ограничения.

```markdown
# CLAUDE.md

## Команды
- Установка: `npm ci` (не `npm install` — используем lock-файл)
- Тесты: `npm run test`, e2e: `npm run test:e2e` (нужен запущенный dev-сервер)
- Линт: `npm run lint:fix`, сборка: `npm run build`

## Соглашения
- Стиль: Prettier + ESLint, конфиги в репозитории — не переопределять вручную
- Коммиты: Conventional Commits (`fix:`, `feat:`, `refactor:`)

## Особенности проекта
- `src/legacy/` — код на поддержке, новые фичи туда не добавлять
- Переменные окружения — в `.env.example`, реальные значения — только через 1Password
- `src/billing/` — критичная логика биллинга, изменения проходят ревью отдельно
```

### Режимы разрешений

- **Новый проект** — подтверждение каждого шага.
- **Знакомый проект** с `.claude/settings.json` (занятие 5) — auto-accept для чтения и тестов, подтверждение — для push и удаления.

Граница — по обратимости действия, не по сложности.

### Структура сессии

**Запрос** → **план** (для нетривиальных задач) → **выполнение** → **проверка** (тесты, линт, дифф). Пропуск плана — частая причина, что агент «уезжает не туда».

**Практика**: установите Claude Code в тестовом репозитории, напишите `CLAUDE.md` по образцу. Сравните итерации агента с командой в файле и без.

## Занятие 2. Навигация и чтение кода

### Read, Glob, Grep

- **Read** — «покажи этот файл» (путь известен).
- **Glob** — «какие файлы существуют по паттерну» (`src/**/*.test.ts`).
- **Grep** — «где встречается эта строка» (`handleLogin`).

«Открой файл авторизации» — обычно Grep-задача, а не Read по угаданному имени.

### Разведка большого проекта

«Объясни архитектуру» — плохой промпт: агент читает наугад или застревает на README. Лучше задать точку входа и глубину:

> «Начни с `src/index.ts`, проследи, как обрабатывается HTTP-запрос от роута до записи в БД. Не читай тесты и конфиги. Дай карту: файл → что делает → что вызывает дальше.»

### Explore-агент

Разведку отдавайте read-only агенту Explore: десятки прочитанных файлов — шум, он мешает точности дальше. Explore возвращает сводку, а не сырые файлы.

- Read-only, проект большой и незнакомый → Explore.
- Файл уже известен по имени и месту → читайте сами.

**Практика**: попросите агента составить карту потока «авторизация пользователя»: вход → middleware → выдача токена → валидация. Зафиксируйте markdown-списком файл : роль.

## Занятие 3. Редактирование, тесты, отладка

### Edit vs Write

**Edit** — точечная замена фрагмента. **Write** — перезапись целиком, только для новых файлов: на существующем риск потерять код, не упомянутый в задаче.

### Правило маленьких диффов

**Плохой промпт**:
> «Почини баг с валидацией email, заодно отрефактори весь модуль форм и добавь типы там, где их нет.»

Дифф на 300+ строк, фикс теряется в шуме.

**Хороший промпт**:
> «`validateEmail()` в `src/forms/validation.ts` принимает `user@domain` без TLD как валидный. Исправь только это.»

```diff
--- a/src/forms/validation.ts
+++ b/src/forms/validation.ts
@@ -12,7 +12,7 @@ export function validateEmail(value: string): boolean {
   if (!value) return false;
-  const pattern = /^[^\s@]+@[^\s@]+$/;
+  const pattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
   return pattern.test(value);
 }
```

Рефакторинг — в отдельную задачу.

### Тесты под существующий код

«Напиши тесты» без уточнений часто даёт тесты, повторяющие реализацию:

> «Тесты для `validateEmail()`: пустая строка, отсутствие `@`, отсутствие TLD, несколько `@`, юникод в локальной части. `describe`/`it`, как в остальных тестах проекта.»

### Падающие тесты

Сообщение о падении содержит `expected`, `received`, стек — не лезьте сразу в стек. Иногда не прав тест, а не код.

### Итеративная отладка

1. **Воспроизвести** — минимальный стабильный сценарий.
2. **Локализовать** — сузить до функции/строки.
3. **Исправить** — минимальное изменение причины, не симптома.
4. **Проверить** — тест зелёный, остальные не сломаны.

Пример — «после обновления профиля счётчик уведомлений не сбрасывается»:

> «После `PATCH /profile` `unreadCount` не обнуляется. Воспроизведи через тестовый клиент, напиши падающий тест в `tests/profile.test.ts`, найди причину в `src/profile/handler.ts` — не исправляй, пока тест не падает стабильно.»

Причина: `updateProfile()` не вызывает `resetNotifications()`.

```diff
--- a/src/profile/handler.ts
+++ b/src/profile/handler.ts
@@ -24,6 +24,7 @@ export async function updateProfile(req: Request, res: Response) {
   const updated = await db.profiles.update(userId, req.body);
+  await resetNotifications(userId);
   res.json(updated);
 }
```

**Практика**: возьмите баг-репорт, пройдите цикл целиком до зелёного теста.

## Занятие 4. Git, ревью, subagents

### Коммиты

Агент формирует сообщение коммита из диффа, но качество зависит от контекста «почему». Не коммитить: секреты, временные логи, закомментированный «на всякий случай» код.

### `/code-review`

Уровни — от `low` до `ultra`. Для точечного фикса хватает `medium`; `ultra` — для миграций и биллинга. Результат — инлайн-комментарии к строкам, не «одобрено/отклонено».

### PR: пример описания

```markdown
## Что

Счётчик непрочитанных уведомлений (`unreadCount`) не сбрасывался после
обновления профиля через `PATCH /profile`.

## Почему

`updateProfile()` в `src/profile/handler.ts` не вызывал `resetNotifications()`,
хотя эта логика уже использовалась в `markAsRead()`. Обработчик профиля был
добавлен позже, про сброс счётчика забыли.

## Изменения

- `src/profile/handler.ts`: добавлен вызов `resetNotifications(userId)`.
- `tests/profile.test.ts`: новый тест на баг (PATCH /profile → count = 0).

## План тестирования

- [x] Новый тест — падал до фикса, зелёный после
- [x] Полный набор тестов — без регрессий (`npm run test`)
- [x] Ручная проверка в dev-окружении: счётчик обнулился в UI
- [ ] Нужна проверка на staging перед мерджем
```

### Subagents: делегировать или нет

Типы: **Explore** (read-only), **Plan** (планирование до кода), **general-purpose** (все инструменты). Критерий — объём шума, не сложность.

- **Делегировать**: «Проверь `src/api/`, найди эндпоинты без валидации».
- **Самому**: «Исправь опечатку в `src/errors.ts`, строка 42».

Plan оправдан, когда неверный подход дорого откатывать (перевод сессий на Redis); для мелкой правки — избыточен.

### Worktree

Для параллельной работы без конфликтов — git worktree: отдельная директория, тот же репозиторий, другая ветка.

**Практика**: прогоните `/code-review` (`medium`+) на баге из занятия 3. Оформите PR по образцу выше.

## Занятие 5. Workflows и настройка поведения

### Когда одного агента недостаточно

Задачи, распадающиеся на независимые подзадачи, быстрее решать фан-аутом на несколько агентов, чем одним в раздувающемся контексте.

### pipeline() vs parallel()

- **parallel()** — независимые задачи одновременно, барьер перед агрегацией. Пример: дифф на 200 строк проверяют три агента сразу — безопасность, производительность, стиль.
- **pipeline()** — последовательно, шаг использует результат предыдущего. Пример: «собери упоминания → проверь достоверность → отчёт».

Шаг Б не ждёт А — parallel; требует результат А — pipeline.

### `.claude/settings.json`

```json
{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Bash(npm run lint:*)", "Bash(git status)", "Bash(git diff:*)"],
    "ask": ["Bash(git push:*)", "Bash(git commit:*)", "Bash(rm:*)"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          { "type": "command", "command": "npm run lint:fix -- $CLAUDE_FILE_PATH" }
        ]
      }
    ]
  }
}
```

Read-only команды — в allowlist, необратимые (push, commit, rm) — с подтверждением. Хук `PostToolUse` на `Edit` прогоняет автофикс после правки.

**Практика**: настройте allowlist read-only команд проекта. Опишите сценарий, где оправдан workflow.

## Итоговый проект модуля

Возьмите open-source репозиторий (или подходящий рабочий проект):

1. **Найдите баг** — через issue-трекер (`good first issue`, `bug`) или своим тестированием.
2. **Настройте `CLAUDE.md`**, если его ещё нет.
3. **Воспроизведите баг**, напишите падающий тест.
4. **Исправьте** минимальным диффом — одна проблема за раз.
5. **Прогоните `/code-review`** минимум на `medium`.
6. **Оформите PR** по структуре «Что / Почему / Изменения / План тестирования».

### Чек-лист проверки

- [ ] `CLAUDE.md` содержит команды и соглашения, не дублирует код
- [ ] Дифф маленький, сфокусирован на одной проблеме
- [ ] Есть тест, стабильно падавший до фикса и зелёный после
- [ ] Полный набор тестов проходит без регрессий
- [ ] PR прошёл `/code-review` минимум на `medium`, замечания устранены
- [ ] Описание PR отвечает на три вопроса: что / почему / как проверено
- [ ] Вы можете объяснить, когда стоило делегировать subagent, а когда нет
