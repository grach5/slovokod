Модуль 1 — про работу внутри одной сессии. Этот модуль — про то, что делать, когда сессии мало: агенту нужно достучаться до внешней системы, повторять задачу без вас или разделить проверку между несколькими агентами. Общий принцип: чем больше автономии у агента, тем осознаннее нужно проектировать её границы — это другой класс системы с другими правилами, а не «промпт помощнее».

## MCP: протокол расширения возможностей

По умолчанию модель не видит ничего за пределами диалога: не может открыть браузер, прочитать файл, дёрнуть API CRM. **MCP (Model Context Protocol)** — открытый протокол, которым внешний «MCP-сервер» описывает модели свои инструменты и данные.

- MCP-сервер знает устройство системы (CRM, БД, API) и оборачивает его в инструменты со схемой входа и выхода — Claude достаточно знать сигнатуру `create_ticket(title, priority)`, а не как устроена CRM изнутри.
- Один протокол работает одинаково для файлового сервера, браузера и внутреннего API — сервер одной команды подключается без переделки к любому MCP-клиенту.

Часть инструментов сервера может быть «отложенной»: клиент видит только название, а схему параметров подгружает по запросу (например, через ToolSearch) — это экономит контекст на инструментах, которые не понадобятся.

### Практика

Найдите в клиенте список подключённых MCP-серверов, выберите готовый (браузер или файловая система) и выполните им реальную задачу — например, извлеките данные со страницы.

## Свой MCP-сервер

MCP раскрывается, когда вы оборачиваете *своё*: внутренний API, БД, скрипт, которым раньше пользовались руками. Минимальный сервер — одна функция плюс метаданные для модели, например сервер статуса заказа по номеру — три части.

1. **Схема инструмента.** Имя (`get_order_status`), описание в одно предложение, строгая схема параметров (`order_id`: строка, обязательное) — контракт, где неверный параметр даёт ошибку валидации, а не догадку.
2. **Server instructions.** Контекст для модели: когда вызывать инструмент, а когда нет («не чаще раза на заказ за сессию»), как трактовать пустой ответ — часть промпта, такая же лаконичная, как системный промпт из Модуля 0.
3. **Реализация.** Обычный код: принимает `order_id`, обращается к источнику, возвращает ответ — та же функция, просто с обвязкой под MCP.

Тестируйте сервер в изоляции, до подключения к агенту: отладка сразу и сервера, и вызовов модели — вдвое дороже.

### Практика

Спроектируйте на бумаге простой MCP-сервер (обёртку над API вашей компании) с одним-двумя инструментами: опишите схему параметров и server instructions для каждого.

## Регулярные задачи: scheduled tasks и `/loop`

Часть работы периодична: проверить метрику каждое утро, собрать сводку раз в неделю. Для этого — **scheduled tasks**: задачи по расписанию без человека в момент запуска, где все решения о допустимой автономии принимаются заранее, на этапе проектирования.

**Важно для безопасности.** Регулярная задача — не разовое действие, а изменение постоянной конфигурации, работающей без вас неделями, как автопересылка почты или вебхук:

- нужно понимать, какие данные она читает, куда уходит результат и как её отключить;
- «настрой еженедельный агент» — не повод молча добавлять выход наружу (письмо, запись в чужую базу, публикация): такой шаг требует явного согласия пользователя, что именно уходит наружу и куда.

Пример — агент еженедельной сводки: открывает дашборд, сравнивает метрики с прошлой неделей, формирует отчёт. Если источник недоступен — пропускает неделю с пометкой об ошибке, а не выдумывает числа.

`/loop` решает смежную задачу иначе: не «по расписанию неделями», а «повторять шаг до завершения» в своём темпе — для конечных задач с условием остановки («проверяй, пока сборка не завершится»), в отличие от cron-задачи, которая идёт, пока её явно не отключат.

### Практика

Спроектируйте регулярную задачу для сценария из своей практики: что проверяется, с какой частотой, куда уходит результат, что при ошибке источника и какой шаг требует явного согласия перед первым запуском.

## Многоагентные workflow

Часть задач распадается на независимые куски или требует нескольких точек зрения — паттерны из Модуля 1 становятся инструментом проектирования, а не способом ускориться.

- **Pipeline** — конвейер: элемент проходит все стадии независимо от остальных. Обрабатывая сто файлов по схеме «прочитать → проанализировать → переписать», не нужно ждать все сто, чтобы начать анализ первого.
- **Parallel с барьером** — агенты работают параллельно, но результат нужен целиком перед следующим шагом: например, для дедупликации находок или раннего выхода, если все проверки вернули «ничего не найдено». Без такой причины барьер лишь заставляет быстрого агента ждать медленного.

Отдельный класс — про качество, не скорость: **адверсариальная проверка** отдаёт находку одного агента на опровержение другим, настроенным на скепсис, вместо того чтобы принять её на веру.

Пример: агент нашёл потенциальный баг. Фрагмент кода и вопрос «баг ли это» уходят трём независимым рецензентам, не видящим вывода друг друга, — каждый голосует «да»/«нет» с обоснованием. Два из трёх «да» — находка подтверждена; голоса разделились почти поровну — сигнал показать человеку. Независимость рецензентов и делает проверку осмысленной — иначе они быстро сойдутся на одном мнении без реальной перепроверки.

### Практика

Спроектируйте workflow для задачи «проверить N файлов на одну проблему (например, отсутствие обработки ошибок) и подтвердить находки независимо»: стадии pipeline, где нужен барьер, устройство адверсариальной проверки (число рецензентов, вход, правило подтверждения).

## Управление контекстом между сессиями

У сессии есть предел длины: рано или поздно история упирается в лимит или сжимается, теряя детали — агент, который знал, какой файл редактировал последним, может это забыть, если деталь не зафиксирована явно.

Есть разница между *контекстом сессии* (что модель видит сейчас, и что стоит денег с каждым токеном) и *памятью* — заметками, файлами состояния, markdown, который агент читает в начале новой сессии.

Полное устройство памяти, экономику токенов и промпт-кэширования разбирает следующий модуль, **«Токены, память и контекст»**. Пока достаточно: то, что не записано явно, при сжатии считается несуществующим.

### Практика

Возьмите свою многошаговую задачу, занявшую больше одной сессии: опишите, что из контекста первой сессии критично не потерять и в каком виде вы бы это сохранили.

## Итоговый проект модуля

Спроектируйте (и, если есть доступ, реализуйте) агента для типичной задачи автоматизации:

1. **Проверяет источник данных** — дашборд, API, файл — по согласованному заранее расписанию.
2. **Обрабатывает результат** — фильтрует шум, сравнивает с предыдущим состоянием.
3. **Решает, нужно ли уведомление** — агент умеет промолчать, если ничего существенного не произошло.
4. **Обрабатывает ошибки** — если источник недоступен, фиксирует сбой, а не подставляет выдуманные данные.

Отдельно зафиксируйте: какой шаг отправляет что-либо во внешнюю систему — и что это согласовано явно перед первым запуском, а не включено по умолчанию.

## Чек-лист проверки

- [ ] Объясняете разницу между MCP-сервером и обычным инструментом на конкретном примере
- [ ] Предусмотрена обработка ошибки или недоступности источника данных — без выдуманных значений
- [ ] Понимаете, когда pipeline, а когда parallel с барьером
- [ ] Автоматизация не шлёт данные наружу без явно согласованного шага
- [ ] Регулярная задача — осознанная постоянная конфигурация, а не разовый запуск
