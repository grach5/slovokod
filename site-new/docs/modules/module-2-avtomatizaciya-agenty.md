Первый модуль научил вас работать с Claude Code внутри одной сессии: читать
код, редактировать файлы, запускать subagents для параллельных задач. Этот
модуль — про то, что происходит, когда одной сессии недостаточно: когда
Claude нужно достучаться до внешней системы, повторять задачу по расписанию
без вас или распределить проверку между несколькими независимыми агентами.

Четыре темы, которые здесь разбираются, объединяет один принцип: чем больше
автономии вы даёте агенту, тем осознаннее нужно проектировать границы этой
автономии. Инструмент, который подключается к внешней системе, задача,
которая запускается без вас каждую неделю, и конвейер из нескольких агентов —
это не «более мощная версия промпта», а другой класс системы, к которому
применяются другие правила.

## MCP: протокол расширения возможностей

По умолчанию у модели нет доступа ни к чему за пределами текущего диалога:
она не может открыть ваш браузер, прочитать файл на диске или дёрнуть API
вашей CRM. **MCP (Model Context Protocol)** — открытый протокол, решающий
именно эту проблему: он описывает единый способ, которым внешняя программа
(«MCP-сервер») сообщает модели, какие инструменты и данные у неё есть, а
модель — как их вызывать.

Смысл в разделении ответственности. MCP-сервер — это обычная программа: она
знает, как достучаться до файловой системы, браузера, базы данных или
стороннего API, и оборачивает эту логику в несколько чётко описанных
инструментов со схемой входа и выхода. Claude не обязан знать, как устроена
ваша CRM изнутри — ему достаточно знать, что есть инструмент
`create_ticket(title, priority)`, и его описание. Один и тот же протокол
работает одинаково для файлового сервера, браузера или внутреннего API
компании — это и даёт эффект экосистемы: сервер, написанный одной командой,
подключается без переделки к любому клиенту, поддерживающему MCP.

Практически это выглядит как список серверов, подключённых к проекту или
клиенту. Часть инструментов сервера может быть загружена сразу, часть —
объявлена «отложенной»: клиент видит только название и общее описание, а
полную схему параметров подгружает по запросу через инструмент вроде
ToolSearch, когда задача действительно требует именно этого инструмента.
Это экономит контекст: не нужно с самого начала диалога тащить в промпт
описания полусотни инструментов, если понадобятся два.

### Практика

Найдите в своём клиенте (Claude Code, Claude Desktop или ином MCP-совместимом
инструменте) список подключённых MCP-серверов. Выберите один готовый сервер
(браузер или файловая система) и выполните с его помощью реальную задачу —
например, откройте страницу и извлеките с неё структурированные данные.
Зафиксируйте, какие именно инструменты сервер предоставил и как были описаны
их параметры.

## Свой MCP-сервер: концептуальный разбор

Подключать готовые серверы полезно, но по-настоящему MCP раскрывается, когда
вы оборачиваете *своё* — внутренний API компании, локальную базу данных,
скрипт, которым раньше пользовались только руками. Минимальный сервер — это
не большая система: одна функция плюс метаданные, которые объясняют модели,
когда и как её вызывать.

Возьмём условный пример: сервер, который отдаёт статус заказа по номеру.
Концептуально он состоит из трёх частей.

1. **Схема инструмента.** Имя (`get_order_status`), описание в одно
   предложение, и строгая схема параметров: обязательное поле `order_id`
   типа строка. Схема — это контракт: модель формирует вызов ровно по ней,
   и лишний или неверно типизированный параметр приведёт к ошибке валидации,
   а не к угадыванию.
2. **Инструкции для агента (server instructions).** Отдельно от схемы
   параметров сервер может дать модели общий контекст: когда вызывать этот
   инструмент, а когда — нет, какие ограничения есть («не вызывать чаще
   одного раза на один и тот же заказ в рамках сессии»), как трактовать
   пустой ответ. Это не документация для человека, а часть промпта,
   которую видит модель, — поэтому она должна быть такой же лаконичной и
   однозначной, как хороший системный промпт из Модуля 0.
3. **Реализация.** Обычный код, который принимает `order_id`, обращается к
   реальному источнику данных (базе, внутреннему API) и возвращает
   структурированный ответ — то же самое, что вы написали бы для обычной
   функции, просто с обвязкой, которая делает эту функцию видимой по
   протоколу MCP.

Ключевая дисциплина здесь — тестировать сервер в изоляции, до подключения
к агенту: вызвать инструмент напрямую с несколькими вариантами входа
(валидный ID, несуществующий ID, пустая строка) и убедиться, что ответы
предсказуемы. Отлаживать одновременно и сам сервер, и то, правильно ли
модель его вызывает, — вдвое дороже по времени, чем сначала убедиться, что
сервер работает сам по себе.

### Практика

Спроектируйте на бумаге (без обязательной реализации, если нет доступа к
рабочему API) простой MCP-сервер с одним-двумя инструментами — обёртку над
внутренним API вашей компании или локальным хранилищем данных. Опишите
схему параметров каждого инструмента и одно-два предложения server
instructions для каждого.

## Регулярные задачи: scheduled tasks и `/loop`

Разовый запуск агента решает разовую задачу. Но часть полезной работы —
периодическая по своей природе: проверить метрику каждое утро, собрать
сводку раз в неделю, отследить изменение цены раз в час. Для этого
существуют **scheduled tasks** — задачи, которые выполняются по расписанию
(по времени суток или по cron-подобному интервалу) без участия человека в
момент запуска.

Разница со обычной сессией принципиальна: scheduled task не спрашивает вас
«можно ли продолжить» в процессе выполнения, потому что в момент запуска
вас может не быть рядом. Значит, все решения о том, что можно делать
автоматически, а что требует подтверждения, должны быть приняты заранее, на
этапе проектирования задачи, а не на этапе её выполнения.

**Важный момент безопасности.** Настройка регулярной задачи — это не разовое
действие вроде «прочитай файл», а изменение постоянной конфигурации: вы
создаёте правило, которое будет запускаться снова и снова без вашего
участия, возможно, неделями. Это тот же класс решений, что настройка
автопересылки почты или постоянного вебхука — и должен приниматься так же
осознанно: с ясным пониманием, какие данные задача читает, куда результат
уходит и как её потом отключить. «Настрой мне еженедельный агент» — не повод
молча создавать конфигурацию с выходом во внешние системы (отправка письма,
запись в чужую базу, публикация куда-либо); прежде чем включать такой шаг,
его нужно явно проговорить с пользователем и получить согласие на то, что
именно будет уходить наружу и куда.

Реалистичный пример — агент еженедельной сводки: раз в неделю он открывает
дашборд аналитики, вытаскивает ключевые метрики, сравнивает с прошлой
неделей и формирует короткий отчёт. Здесь важно спроектировать не только
«счастливый путь», но и отказ: что делать, если источник данных недоступен
в момент запуска (пропустить неделю с пометкой об ошибке — не притворяться,
что всё в порядке, и не заполнять отчёт выдуманными числами), и куда должен
попасть готовый отчёт — это тоже часть согласованной заранее конфигурации,
а не решение, принимаемое агентом на лету.

`/loop` решает смежную, но другую задачу: не «выполняться по расписанию
неделями», а «повторять шаг за шагом одну задачу до её завершения» — с
самостоятельно выбираемым темпом, а не жёстким интервалом. Это подходит для
случаев вроде «проверяй каждые несколько минут, пока сборка не завершится»
или «повторяй проверку, пока значение не изменится» — то есть для конечных
по своей природе задач, у которых есть условие остановки, в отличие от
по-настоящему постоянной cron-задачи, которая продолжается, пока её явно не
отключат.

### Практика

Спроектируйте (не обязательно запуская по-настоящему) регулярную задачу для
рабочего сценария из вашей практики: что именно проверяется, с какой
частотой, куда уходит результат и — обязательно — что происходит при
ошибке источника. Отдельно пропишите: какой шаг в этой задаче требует
явного согласия пользователя перед первым запуском, и почему.

## Многоагентные workflow

Одна сессия с одним агентом хорошо справляется с задачами, которые
укладываются в линейный ход мысли. Но часть задач по своей структуре
распадается на независимые куски или требует нескольких точек зрения — и
здесь на сцену выходят многоагентные паттерны из Модуля 1, но уже как
осознанный инструмент проектирования, а не как способ ускориться.

**Pipeline** — конвейер: каждый элемент проходит все стадии независимо от
остальных, стадии не ждут друг друга по всей партии сразу. Если вы
обрабатываете сто файлов и для каждого нужно «прочитать → проанализировать
→ переписать», нет причин ждать, пока все сто файлов будут прочитаны, прежде
чем начать анализ первого. Барьер здесь не нужен и только замедляет работу.

**Parallel с барьером** — противоположный случай: несколько агентов
работают параллельно, но результат нужен целиком, прежде чем двигаться
дальше. Барьер оправдан, когда следующий шаг зависит от совокупности всех
результатов сразу — например, дедупликация находок нескольких агентов
(без барьера вы не узнаете, какие находки — дубликаты) или ранний выход,
если все параллельные проверки независимо друг от друга вернули «ничего не
найдено». Барьер неоправдан, когда он просто заставляет более быстрого
агента ждать более медленного без содержательной причины.

Отдельный класс паттернов — про качество, а не про скорость.
**Адверсариальная проверка** — это когда находку одного агента не
принимают на веру, а отдают на независимое опровержение другому агенту (или
нескольким), явно настроенным на скепсис. Простой пример: агент нашёл
потенциальный баг в коде. Вместо того чтобы сразу считать его подтверждённым,
задача уходит трём независимым «агентам-рецензентам»: каждый получает тот же
фрагмент кода и вопрос «баг ли это на самом деле», но не видит вывода
остальных, — и голосует «да» или «нет» со своим обоснованием. Если два из
трёх говорят «да», находка считается подтверждённой; если мнения
разделились почти поровну, это сигнал показать находку человеку, а не
доверять первому агенту, который мог ошибочно увидеть проблему там, где её
нет. Независимость рецензентов — это то, что делает проверку осмысленной:
если дать всем троим видеть вывод друг друга, они быстро сойдутся на первом
мнении, и весь смысл перепроверки потеряется.

### Практика

Спроектируйте workflow для задачи «проверить N файлов проекта на одну и ту
же потенциальную проблему (например, отсутствие обработки ошибок) и
подтвердить находки независимо». Определите: какие стадии образуют pipeline,
где нужен барьер и почему, и как именно устроена адверсариальная проверка
находок — сколько агентов-рецензентов, что именно они получают на вход и
по какому правилу находка считается подтверждённой.

## Управление контекстом между сессиями

У любой сессии есть предел длины: рано или поздно история диалога либо
упирается в лимит контекста, либо начинает автоматически сжиматься. При
сжатии часть деталей неизбежно теряется — и агент, который десять минут
назад точно знал, какой файл он последним редактировал и почему, может
через сжатие эту деталь потерять, если она не была зафиксирована явно.

Есть разница между *контекстом одного чата* — тем, что модель видит прямо
сейчас, — и *памятью*, которая переживает конец сессии: явные заметки,
промежуточные файлы состояния, структурированные markdown-файлы, которые
агент читает в начале новой сессии и понимает, на чём остановился. Разница
принципиальна: контекст эфемерен и стоит денег с каждым лишним токеном,
память — это то, что вы сознательно решаете сохранить между сессиями,
потому что без неё работа начинается с нуля каждый раз.

Здесь мы намеренно останавливаемся на поверхностном уровне: полное
устройство паттерна памяти между сессиями, экономика токенов и
промпт-кэширования, и то, что из громких заявлений про «экономию контекста»
правда, а что — маркетинг, — тема отдельного модуля **«Токены, память и
контекст»**, идущего сразу после этого. Здесь достаточно зафиксировать
главное: то, что не записано явно, при сжатии контекста считается
несуществующим, поэтому дизайн долгоживущих агентов начинается с вопроса
«что из происходящего сейчас понадобится мне через сто сообщений — и где
это будет храниться».

### Практика

Возьмите любую свою многошаговую задачу, которая заняла больше одной сессии
(или могла бы занять). Опишите: что из контекста первой сессии было бы
критично не потерять, и в каком виде (файл, заметка, структура) вы бы это
сохранили, чтобы вторая сессия могла продолжить без потери качества.

## Итоговый проект модуля

Спроектируйте и, если позволяет доступ, реализуйте агента, который решает
типичную задачу автоматизации целиком:

1. **Регулярно проверяет источник данных** — дашборд, API, файл, страницу —
   по согласованному заранее расписанию.
2. **Обрабатывает результат** — фильтрует шум, сравнивает с предыдущим
   состоянием, выделяет значимые изменения.
3. **Формирует отчёт и решает, нужно ли уведомление** — не каждая проверка
   должна заканчиваться сообщением человеку; агент должен уметь решить
   «сегодня ничего существенного не произошло» и промолчать.
4. **Обрабатывает ошибки** — что происходит, если источник недоступен в
   момент запуска: агент обязан явно зафиксировать сбой, а не подставить
   правдоподобные, но выдуманные данные вместо реальных.

Отдельно письменно зафиксируйте: какой шаг этого агента отправляет что-либо
во внешнюю систему (письмо, сообщение, запись в чужую базу) — и подтвердите,
что перед первым реальным запуском этот шаг согласован явно, а не включён
по умолчанию.

## Чек-лист проверки

- [ ] Вы можете объяснить разницу между MCP-сервером и обычным инструментом
      своими словами, на конкретном примере
- [ ] В проекте предусмотрена обработка ошибки или недоступности источника
      данных — без подстановки правдоподобных, но выдуманных значений
- [ ] Вы понимаете, когда использовать pipeline, а когда parallel с барьером,
      и можете привести пример каждого
- [ ] Автоматизация не отправляет данные во внешние системы без отдельного,
      явно согласованного шага подтверждения
- [ ] Регулярная задача спроектирована как осознанная постоянная
      конфигурация, а не как «ещё один разовый запуск»
