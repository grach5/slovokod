**Время**: ~5 частей по 90 мин | **Пререквизиты**:
[Модуль 0](./module-0-osnovy-promptinga.md), уверенное владение хотя бы одним
языком программирования

Здесь Claude становится частью *вашего* приложения, а не отдельным инструментом.
Вы отвечаете за структуру запроса, обработку ошибок, стоимость вызова и архитектуру
цикла «модель ↔ инструменты ↔ пользователь». Код в примерах — иллюстративный
псевдокод на Python: он показывает структуру решения, а не подходит для копирования
один в один. Точные имена методов и параметры конкретного SDK всегда сверяйте с
документацией Anthropic.

## Занятие 1: Messages API — основы

- Один HTTP-эндпоинт: модель + системный промпт + история сообщений → ответ.
- История передаётся целиком при каждом запросе — API не хранит состояние между
  вызовами, это ваша ответственность.
- Роли чередуются (`user` → `assistant` → `user`…). Системный промпт — отдельное
  поле, а не первое сообщение в списке.

```python
from claude_client import Client   # иллюстративное имя SDK

client = Client(api_key=env["ANTHROPIC_API_KEY"])

response = client.messages.create(
    model="claude-sonnet",
    max_tokens=1024,
    system="Ты — ассистент поддержки. Отвечай кратко, по-русски, не выдумывай факты.",
    messages=[{"role": "user", "content": "Где посмотреть статус моего заказа?"}],
)

print(response.content[0].text)
print(response.stop_reason)   # конец ответа, лимит токенов, вызов инструмента...
```

Для чат-интерфейса ответ целиком — плохой UX: пользователь смотрит на пустой экран,
пока модель думает. Стриминг решает это — сервер присылает ответ кусками.

```python
with client.messages.stream(
    model="claude-sonnet", max_tokens=1024,
    system="Отвечай примерами кода, без лишних вступлений.",
    messages=[{"role": "user", "content": "Разница между list и tuple в Python?"}],
) as stream:
    for event in stream:
        if event.type == "text_delta":
            print(event.text, end="", flush=True)
    final_message = stream.get_final_message()
```

Из параметров генерации на практике важны:

- **`max_tokens`** — жёсткий потолок длины ответа. При достижении ответ обрывается
  на середине слова — это не ошибка, а `stop_reason: "max_tokens"`.
- **Стоп-последовательности** — строки, при появлении которых модель останавливается
  сама.
- **Температура и effort** — баланс «предсказуемость / разнообразие». На новых
  моделях Claude всё больше решает параметр «уровень усилия» (effort) и адаптивное
  рассуждение — сверяйте набор параметров с документацией SDK, не с памятью.
- **Ошибки** — штатная часть цикла, а не исключение: превышение лимита запросов
  (подождать и повторить), неверный запрос (не повторять бездумно, а чинить payload),
  временная перегрузка сервиса, таймаут (запрос не дождался ответа за отведённое
  время — обычно стоит повторить с постепенно увеличивающейся паузой, retry с
  backoff). Профессиональный клиент обрабатывает их по типу, а не одним общим
  `except`.

**Практика**: минимальный консольный чат-клиент со стримингом — цикл «прочитать
ввод → добавить в историю → стримить ответ → добавить ответ модели в историю →
повторить», с корректным откликом на ошибку лимита запросов.

## Занятие 2: Tool use

Инструмент (tool) — описание функции, которую умеет вызывать *ваш* код, а не
модель. Модель не выполняет код сама: она решает, что нужно вызвать инструмент, и
возвращает структурированный запрос на вызов. Цикл: модель просит вызов → ваш код
исполняет реальную функцию → результат возвращается как ещё одно сообщение → модель
отвечает или просит следующий вызов.

```python
tools = [{
    "name": "get_weather",
    "description": "Вернуть текущую погоду по названию города",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

history = [{"role": "user", "content": "Стоит ли брать зонт в Питере сегодня?"}]
response = client.messages.create(model="claude-sonnet", max_tokens=1024, tools=tools, messages=history)

while response.stop_reason == "tool_use":
    history.append({"role": "assistant", "content": response.content})
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            try:
                result = run_local_tool(block.name, block.input)   # ваша реальная функция
                tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(result)})
            except Exception as e:
                tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(e), "is_error": True})
    history.append({"role": "user", "content": tool_results})
    response = client.messages.create(model="claude-sonnet", max_tokens=1024, tools=tools, messages=history)

print(response.content[0].text)
```

Детали, которые чаще всего ломают этот цикл:

- `description` должен объяснять не только *что* делает функция, но и *когда* её
  вызывать — модель решает на основе текста описания, а не имени функции.
- Если модель просит несколько инструментов за один ответ, все результаты
  возвращаются **одним** сообщением — иначе модель постепенно перестаёт запрашивать
  параллельные вызовы.
- Ошибку выполнения не нужно прятать: верните её как результат с пометкой
  `is_error`, модель обычно сама скорректирует следующий шаг.
- `tool_choice` принудительно вызывает конкретный инструмент — полезно, когда нужен
  гарантированно структурированный результат (JSON), а не свободный текст.

**Практика**: инструмент «курс валюты» или «калькулятор» и полный цикл — от
запроса пользователя до финального ответа с учётом результата вызова.

## Занятие 3: Prompt caching и оптимизация стоимости

Каждый вызов API оплачивается по токенам на входе и на выходе. Если системный
промпт содержит объёмную базу знаний или список инструментов, неизменных от
запроса к запросу, эти токены можно закэшировать: при повторном использовании
того же префикса модель читает его из кэша, а не обрабатывает заново.

```python
LONG_SYSTEM_PROMPT = load_knowledge_base()   # например, 30 страниц документации

response = client.messages.create(
    model="claude-sonnet", max_tokens=1024,
    system=[{"type": "text", "text": LONG_SYSTEM_PROMPT, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": user_question}],
)

print(response.usage.cache_read_input_tokens)      # из кэша (дёшево)
print(response.usage.cache_creation_input_tokens)  # запись в кэш (дороже разового вызова)
```

- Кэш — это **совпадение префикса**: если хоть один байт в начале запроса меняется
  (дата, ID пользователя), всё, что идёт после этого места, кэшируется заново.
- Стабильный контент (инструкции, список инструментов, статичный документ) должен
  идти раньше по порядку; изменчивое (вопрос пользователя, метки времени) — позже.
- Первый вызов с новым префиксом всегда платит немного дороже (запись в кэш);
  выигрыш появляется со второго и последующих обращений к тому же префиксу.
- Кэширование выгодно там, где один и тот же объёмный контекст переиспользуется
  много раз подряд (агент с постоянной спецификацией API, чат-бот с длинной базой
  знаний), и почти бесполезно там, где контекст каждый раз уникален.

Актуальные цены за токены (обычный вход/выход, запись в кэш, чтение из кэша)
смотрите на странице [цен Anthropic](https://platform.claude.com/docs/en/pricing) —
цифры меняются, поэтому в модуле их не фиксируем. Порядок величины ориентировочно
такой: чтение из кэша стоит в несколько раз дешевле обычного входного токена, а
запись в кэш — немного дороже обычного входного токена.

**Практика**: возьмите сценарий «чат-бот с длинной базой знаний в системном
промпте», подставьте актуальные цены со страницы pricing и на бумаге посчитайте
разницу в стоимости 100 запросов с кэшированием и без — чтобы прочувствовать
порядок величины экономии на конкретном случае.

## Занятие 4: Agent SDK и управляемая песочница

Всё выше — это вызовы, которые вы оркеструете сами: пишете цикл, сами решаете,
когда остановиться, сами храните историю. Agent SDK устраняет эту ручную работу
там, где агенту нужно самостоятельно провести многошаговое рассуждение с
инструментами — прочитать файл, отредактировать, запустить команду, проверить
результат, повторить. Вы описываете доступные инструменты и системную инструкцию,
а SDK берёт на себя сам агентный цикл.

```python
from claude_agent_sdk import Agent, tool   # иллюстративное имя SDK

@tool
def search_internal_docs(query: str) -> str:
    """Найти релевантный фрагмент во внутренней базе знаний компании."""
    return internal_search_index.query(query)

@tool
def create_support_ticket(summary: str, priority: str) -> str:
    """Завести тикет в трекере поддержки и вернуть его номер."""
    return ticketing_api.create(summary=summary, priority=priority)

agent = Agent(
    model="claude-sonnet",
    instructions="Ты — бот первой линии поддержки. Сначала ищи ответ через search_internal_docs; если решения нет — заводи тикет.",
    tools=[search_internal_docs, create_support_ticket],
)

result = agent.run("Клиент спрашивает, как экспортировать отчёт в CSV")
print(result.final_output)
```

Докстринг функции (текст в тройных кавычках) становится описанием инструмента,
которое видит модель, — как и `description` в Занятии 2. Пишите его для модели,
а не только для себя как для программиста.

Отдельный вопрос — где исполняется код инструментов. Когда агенту нужно не просто
вызывать ваши функции, а самому исполнять код и работать с файлами в изолированном
окружении, есть **управляемая песочница** (managed sandbox): Anthropic поднимает
контейнер на сессию, агентный цикл идёт на стороне Anthropic, а ваши файлы и
инструменты подключаются к сессии, а не разворачиваются на вашей инфраструктуре.
Это снимает с вас заботу о контейнерах и сетевой изоляции.

Что когда использовать — вопрос сложности задачи и цены ошибки:

- Простой запрос-ответ или один инструмент → обычный вызов Messages API.
- Открытое число итераций, агент сам исследует проблему и правит план → Agent SDK.
- Долгоживущая сессия с изолированным исполнением кода → управляемая песочница.

Не каждой задаче нужен агент: если сценарий укладывается в один предсказуемый
вызов с инструментом, не усложняйте архитектуру ради идеи «сделать агента».

**Практика**: агент с 1–2 кастомными инструментами под конкретную задачу студента
(например, «искать по локальной базе FAQ, а если не найдено — формулировать вопрос
для эскалации человеку»).

## Занятие 5: Мультимодальность и выбор модели

Claude принимает не только текст. Изображения и документы (включая PDF)
передаются в том же сообщении, что и текстовый вопрос — как дополнительные блоки
содержимого в base64 или по ссылке.

```python
import base64

with open("screenshot.png", "rb") as f:
    image_b64 = base64.b64encode(f.read()).decode()
with open("invoice.pdf", "rb") as f:
    pdf_b64 = base64.b64encode(f.read()).decode()

response = client.messages.create(
    model="claude-sonnet", max_tokens=1024,
    messages=[{"role": "user", "content": [
        {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": image_b64}},
        {"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": pdf_b64}},
        {"type": "text", "text": "Сравни сумму на скриншоте оплаты с суммой в PDF-счёте."},
    ]}],
)
```

Ограничения практические: предел размера запроса, число страниц у документов,
разрешение изображений. Проверяйте актуальные лимиты перед обработкой
многостраничных PDF или изображений высокого разрешения — это меняется быстрее,
чем структура запроса.

Выбор модели — вопрос соответствия задаче и бюджету, не «взять самую мощную»:

| Модель | Сильная сторона | Когда выбирать |
|---|---|---|
| **Haiku** | Самая быстрая и дешёвая | Массовая классификация, извлечение полей, большой объём однотипных запросов |
| **Sonnet** | Баланс цены и качества | Рабочая лошадка большинства продуктов — чат-боты, ассистенты, обычные агенты |
| **Opus** | Глубокое рассуждение и агентные задачи | Сложная многошаговая логика, длинные автономные сессии, код с высокой ценой ошибки |

Начинайте с более дешёвой модели, поднимайтесь только когда качества не хватает.
Иногда правильный ответ — не одна модель на весь пайплайн, а комбинация: дешёвая
фильтрует основной поток, дорогая подключается на сложных случаях. Как считать
реальную стоимость сценария — в отдельном
[модуле «Токены, память и контекст»](./module-2t-tokeny-pamyat-kontekst.md).

**Практика**: для трёх сценариев — массовая классификация обращений, сложный
аналитический ассистент, творческий генератор текста — обосновать выбор модели по
цене, скорости и качеству, письменно, в 2–3 предложениях на сценарий.

## Итоговый проект модуля

Консольное или веб-приложение на Claude API с минимум одним инструментом (tool
use) и письменным обоснованием выбора модели под задачу и бюджет. Развитие
практики из занятий 1–2 или новая идея — важно пройти полный цикл: запрос →
возможный вызов инструмента → обработка результата → финальный ответ, а не просто
один вызов API.

## Критерии проверки

- [ ] Цикл вызова инструмента работает от начала до конца, включая несколько
      вызовов подряд
- [ ] Обработаны базовые ошибки API (лимит запросов, таймаут) — по типу, а не
      одним общим `except`
- [ ] Есть письменное обоснование выбора модели (цена / скорость / качество)
- [ ] Студент может объяснить, что кэшируется в его сценарии и почему порядок
      контента в запросе на это влияет
- [ ] Если приложение потоковое — вывод появляется по мере генерации, а не одним
      блоком в конце
