До этого момента вы работали с Claude через готовые интерфейсы — чат, Claude Code,
артефакты. Этот модуль — переход на следующий уровень: Claude становится
компонентом *вашего* приложения, а не отдельным инструментом, в который вы заходите
сами. Разница принципиальная: теперь вы отвечаете за структуру запроса, обработку
ошибок, стоимость каждого вызова и архитектуру цикла «модель ↔ инструменты ↔
пользователь». Ниже — пять занятий, которые проведут вас от одного вызова API до
собственного агента с управляемой песочницей. Код в примерах — иллюстративный
псевдокод на Python, задача которого — показать структуру решения, а не быть
скопированным один в один из документации Anthropic; для точных имён методов и
актуальных параметров конкретного SDK всегда сверяйтесь с официальной
документацией.

## Занятие 1: Messages API — основы

В основе всего — один HTTP-эндпоинт: вы отправляете модель, системный промпт и
историю сообщений, получаете ответ. История передаётся целиком при каждом запросе —
API не хранит состояние между вызовами, это ваша ответственность. Роли в истории
должны чередоваться (`user` → `assistant` → `user`…), а системный промпт — это
отдельное поле, а не первое сообщение в списке: он задаёт роль и правила поведения
модели на весь запрос.

```python
from claude_client import Client   # иллюстративное имя SDK

client = Client(api_key=env["ANTHROPIC_API_KEY"])

response = client.messages.create(
    model="claude-sonnet",
    max_tokens=1024,
    system=(
        "Ты — ассистент поддержки интернет-магазина. Отвечай кратко, "
        "по-русски, и не придумывай номера заказов, которых нет в контексте."
    ),
    messages=[
        {"role": "user", "content": "Где посмотреть статус моего заказа?"},
    ],
)

print(response.content[0].text)
print(response.stop_reason)   # почему модель остановилась: конец ответа, лимит токенов, вызов инструмента...
```

Для чат-интерфейса ответ целиком — плохой UX: пользователь смотрит на пустой экран,
пока модель думает. Потоковая передача (streaming) решает это — сервер присылает
ответ кусками (chunks) по мере генерации, и интерфейс показывает текст по мере
поступления, а не одним куском в конце.

```python
history = [{"role": "user", "content": "Объясни разницу между list и tuple в Python"}]

with client.messages.stream(
    model="claude-sonnet",
    max_tokens=1024,
    system="Отвечай примерами кода, без лишних вступлений.",
    messages=history,
) as stream:
    for event in stream:
        if event.type == "text_delta":
            print(event.text, end="", flush=True)
    final_message = stream.get_final_message()   # полный ответ, когда стрим закончится
```

Из параметров генерации на практике важны прежде всего `max_tokens` (жёсткий
потолок длины ответа — при его достижении ответ обрывается на середине слова, это
не ошибка, а `stop_reason: "max_tokens"`) и стоп-последовательности (строки, при
появлении которых модель прерывается сама). Классические ручки вроде температуры
управляют балансом «предсказуемость / разнообразие» ответа, но на актуальных
моделях Claude поведение генерации всё чаще регулируется параметром «уровень
усилия» (effort) и адаптивным рассуждением, а не только температурой — точный
набор параметров стоит всегда проверять в актуальной документации SDK, а не
полагаться на память о том, «как было раньше».

Ошибки — не исключение, а штатная часть цикла: превышение лимита запросов в минуту,
таймаут, временная перегрузка сервиса. Профессиональный клиент всегда оборачивает
вызов в обработку по типу ошибки (лимит — подождать и повторить, неверный запрос —
не повторять бездумно, а чинить payload) вместо одного общего `except`.

**Практика**: собрать минимальный консольный чат-клиент с потоковым выводом —
цикл «прочитать ввод пользователя → добавить в историю → стримить ответ → добавить
ответ модели в историю → повторить», с корректным откликом на ошибку лимита
запросов.

## Занятие 2: Tool use

Инструмент (tool) — это описание функции, которую умеет вызывать *ваш* код, а не
модель. Модель никогда не выполняет код сама: она решает, что нужно вызвать
инструмент с такими-то аргументами, и возвращает эту просьбу в виде структурированного
блока. Дальше цикл выглядит так: модель просит вызов → ваш код исполняет реальную
функцию → результат возвращается модели как ещё одно сообщение → модель либо
отвечает пользователю, либо просит следующий вызов.

```python
tools = [
    {
        "name": "get_weather",
        "description": "Вернуть текущую погоду по названию города",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "Город, например Москва"}},
            "required": ["city"],
        },
    }
]

history = [{"role": "user", "content": "Стоит ли брать зонт в Питере сегодня?"}]

response = client.messages.create(
    model="claude-sonnet", max_tokens=1024, tools=tools, messages=history,
)

# Полный цикл: пока модель просит вызов инструмента — исполняем и возвращаем результат
while response.stop_reason == "tool_use":
    history.append({"role": "assistant", "content": response.content})

    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            result = run_local_tool(block.name, block.input)   # ваша реальная функция
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": str(result),
            })

    history.append({"role": "user", "content": tool_results})
    response = client.messages.create(
        model="claude-sonnet", max_tokens=1024, tools=tools, messages=history,
    )

print(response.content[0].text)
```

Ключевые детали, которые чаще всего ломают этот цикл на практике: описание
инструмента (`description`) должно объяснять модели не только *что* делает функция,
но и *когда* её вызывать — модель принимает решение о вызове именно на основе
текста описания, а не имени функции. Если модель просит несколько инструментов
за один ответ, все результаты нужно вернуть **одним** сообщением, а не по одному —
иначе модель постепенно перестаёт запрашивать параллельные вызовы. Ошибку
выполнения инструмента не нужно прятать — верните её как результат с пометкой
ошибки, модель обычно сама скорректирует следующий шаг.

Отдельный приём — принудительный вызов конкретного инструмента (`tool_choice`),
когда вам не нужен свободный ответ текстом, а нужен гарантированно структурированный
результат — например, извлечь из письма клиента набор полей (имя, номер заказа,
суть проблемы) строго в виде JSON, а не в виде абзаца текста.

**Практика**: реализовать инструмент «получить курс валюты» или «посчитать
математическое выражение» и провести полный цикл — от запроса пользователя до
финального ответа модели с учётом результата вызова.

## Занятие 3: Prompt caching и оптимизация стоимости

Каждый вызов API оплачивается по количеству токенов на входе и на выходе. Если
системный промпт содержит объёмную базу знаний или список инструментов, которые не
меняются от запроса к запросу, эти токены можно закэшировать: при повторном
использовании того же префикса запроса модель не обрабатывает его заново с нуля,
а читает из кэша — это заметно быстрее и дешевле, чем полная обработка.

```python
LONG_SYSTEM_PROMPT = load_knowledge_base()   # например, 30 страниц документации продукта

response = client.messages.create(
    model="claude-sonnet",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": LONG_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"},   # пометка: закэшировать этот блок
        },
    ],
    messages=[{"role": "user", "content": user_question}],
)

print(response.usage.cache_read_input_tokens)     # сколько токенов пришло из кэша (дёшево)
print(response.usage.cache_creation_input_tokens)  # сколько токенов записано в кэш только что (дороже разового вызова)
print(response.usage.input_tokens)                 # некэшированный остаток
```

Здесь важно понимать границу применимости, а не воспринимать кэширование как
универсальную кнопку «сделать дешевле». Кэш — это **совпадение префикса**: если
хоть один байт в начале запроса меняется (например, вы вставляете в системный
промпт текущую дату или ID пользователя), всё, что идёт после этого места,
кэшируется заново. Значит, стабильный контент (системные инструкции, список
инструментов, статичный документ) должен идти раньше по порядку, а всё изменчивое
(конкретный вопрос пользователя, временные метки) — позже. Первый вызов с новым
префиксом всегда платит немного дороже обычного (запись в кэш), а выигрыш
появляется только начиная со второго и последующих обращений к тому же префиксу.
Поэтому кэширование выгодно там, где один и тот же объёмный контекст переиспользуется
много раз подряд — агент, который снова и снова обращается к одной и той же
спецификации API, или чат-бот с длинной статичной базой знаний — и почти
бесполезно там, где контекст каждый раз уникален.

**Практика**: взять типовой сценарий — чат-бот с длинной базой знаний в системном
промпте — и на бумаге (или в таблице) посчитать разницу в стоимости 100 запросов
с кэшированием и без, чтобы прочувствовать порядок величины экономии на конкретном
случае, а не поверить абстрактному проценту из рекламного материала.

## Занятие 4: Agent SDK и управляемая песочница

Всё, что было выше, — это вызовы, которые вы оркеструете сами: вы пишете цикл,
сами решаете, когда остановиться, сами храните историю. Agent SDK устраняет эту
ручную работу для класса задач, где агенту нужно самостоятельно провести
многошаговое рассуждение с инструментами — прочитать файл, отредактировать его,
запустить команду, проверить результат, повторить. Вместо того чтобы писать цикл
«вызов → инструмент → возврат результата» руками, вы описываете доступные
инструменты и системную инструкцию, а SDK берёт на себя сам агентный цикл.

```python
from claude_agent_sdk import Agent, tool

@tool
def search_internal_docs(query: str) -> str:
    """Найти релевантный фрагмент во внутренней базе знаний компании."""
    return internal_search_index.query(query)

@tool
def create_support_ticket(summary: str, priority: str) -> str:
    """Завести тикет в трекере поддержки и вернуть его номер."""
    return ticketing_api.create(summary=summary, priority=priority)

agent = Agent(
    model="claude-sonnet",
    instructions=(
        "Ты — бот первой линии поддержки. Сначала ищи ответ через "
        "search_internal_docs; если решения нет — заводи тикет."
    ),
    tools=[search_internal_docs, create_support_ticket],
)

result = agent.run("Клиент спрашивает, как экспортировать отчёт в CSV, "
                    "в интерфейсе такой кнопки не видно")
print(result.final_output)
```

Отдельный вопрос — где физически исполняется код инструментов. Для задач, где
агенту нужно не просто вызывать ваши функции, а самостоятельно выполнять код,
работать с файлами и получать результат в изолированном окружении, существует
управляемая песочница (managed sandbox): Anthropic поднимает отдельный
контейнер на сессию, агентный цикл выполняется на стороне Anthropic, а ваши
инструменты и файлы подключаются к этой сессии, а не разворачиваются на вашей
инфраструктуре. Это удобно, когда вы не хотите сами держать и защищать среду
исполнения (контейнеры, доступ к файловой системе, изоляцию сети) — Anthropic
берёт эту часть на себя, а вы описываете задачу и подключаете нужные ресурсы
(файлы, репозиторий, учётные данные для внешних сервисов через отдельное
хранилище секретов).

Когда достаточно прямого Messages API с ручным циклом инструментов, а когда
нужен полноценный агентный SDK или управляемая песочница — вопрос сложности
задачи и цены ошибки. Простой запрос-ответ или один инструмент — обычный вызов
API. Многошаговая задача с открытым числом итераций, где агенту нужно
самостоятельно исследовать проблему и скорректировать план по ходу дела —
кандидат на Agent SDK. Долгоживущая, воспроизводимая, версионируемая сессия с
изолированным исполнением кода — управляемая песочница. Не каждой задаче
нужен агент: если сценарий укладывается в один предсказуемый вызов с инструментом,
не усложняйте архитектуру ради самой идеи «сделать агента».

**Практика**: собрать простого агента с 1–2 кастомными инструментами под
конкретную задачу студента (например, «искать по локальной базе FAQ и предлагать
ответ, а если не найдено — формулировать вопрос для эскалации человеку»).

## Занятие 5: Мультимодальность и выбор модели

Claude принимает на вход не только текст. Изображения и документы (в том числе
PDF) передаются в том же сообщении, что и текстовый вопрос — как дополнительные
блоки содержимого, закодированные в base64 или переданные по ссылке.

```python
import base64

with open("screenshot.png", "rb") as f:
    image_b64 = base64.b64encode(f.read()).decode()

with open("invoice.pdf", "rb") as f:
    pdf_b64 = base64.b64encode(f.read()).decode()

response = client.messages.create(
    model="claude-sonnet",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": image_b64}},
            {"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": pdf_b64}},
            {"type": "text", "text": "Сравни сумму на скриншоте оплаты с суммой в PDF-счёте и укажи расхождение."},
        ],
    }],
)
```

Ограничения здесь практические, а не теоретические: у запроса есть предел размера
(суммарный вес вложений и текста), у документов — предел числа страниц, у
изображений — предел разрешения, выше которого модель не получает дополнительной
пользы, а вы платите за лишние токены. Перед тем как закладывать в продукт
обработку многостраничных PDF или изображений высокого разрешения, проверяйте
актуальные лимиты — они относятся к тем деталям, которые меняются между версиями
моделей быстрее, чем структура запроса.

Выбор модели — не вопрос «взять самую мощную», а вопрос соответствия задаче и
бюджету. У линейки Claude четыре ориентира:

| Модель | Сильная сторона | Когда выбирать |
|---|---|---|
| **Haiku** | Самая быстрая и дешёвая | Массовая классификация, извлечение полей, обработка большого объёма однотипных запросов |
| **Sonnet** | Баланс цены и качества | Рабочая лошадка большинства продуктовых сценариев — чат-боты, ассистенты, обычные агенты |
| **Opus** | Глубокое рассуждение и агентные задачи | Сложная многошаговая логика, длинные автономные сессии, код с высокой ценой ошибки |
| **Fable** | Максимальная доступная способность рассуждать | Самые трудные задачи на пределе возможностей модели — не для повседневного объёма из-за цены |

Практическое правило: начинайте с более дешёвой модели и поднимайтесь выше только
там, где показали, что качества не хватает, а не наоборот. Иногда правильный
ответ — не одна модель на весь пайплайн, а комбинация: дешёвая модель фильтрует
и классифицирует основной поток, а дорогая подключается только на сложных
случаях, которые прошли первый фильтр. Подробный разбор того, как считать
реальную стоимость сценария, что действительно экономит токены, а что —
маркетинговый миф, вынесен в отдельный
[модуль «Токены, память и контекст»](./module-2t-tokeny-pamyat-kontekst.md) —
он рассматривает эту тему глубже, чем позволяет формат одного занятия здесь.

**Практика**: для трёх гипотетических продуктовых сценариев — массовая
классификация обращений, сложный аналитический ассистент для разбора отчётов,
творческий генератор текста — обосновать выбор модели с учётом цены, скорости и
требуемого качества, письменно, в 2–3 предложениях на сценарий.

## Итоговый проект модуля

Собственное консольное или веб-приложение на Claude API с минимум одним
инструментом (tool use) и явным письменным обоснованием выбора модели под задачу
и бюджет. Это может быть развитием практики из занятий 1–2 (чат-клиент с
инструментом) или полностью новая идея студента — важно, чтобы приложение
проходило полный цикл: запрос → возможный вызов инструмента → обработка
результата → финальный ответ, а не просто демонстрировало один вызов API.

## Критерии проверки

- [ ] Приложение корректно обрабатывает цикл вызова инструмента от начала до конца,
      включая случай нескольких вызовов подряд
- [ ] Обработаны базовые ошибки API (превышение лимита запросов, таймаут) —
      не одним общим `except`, а по типу ошибки
- [ ] Есть письменное обоснование выбора модели с учётом цены, скорости и качества
- [ ] Студент может объяснить, что именно кэшируется в его сценарии и почему
      порядок контента в запросе на это влияет
- [ ] Если приложение потоковое — вывод действительно появляется по мере генерации,
      а не одним блоком в конце
