**Поток**: Практик / Инженер · **Длительность**: 2 занятия по 90 минут · **Пререквизиты**: Модули 1, 2

К этому модулю вы уже умеете работать с Claude Code, подключать MCP-серверы и
собирать агентов. Осталась последняя, самая практичная часть: как встроить
Claude в рабочий процесс *команды*, а не только в свой терминал. Частая
ошибка на этом этапе — тащить один и тот же инструмент во все сценарии подряд
(«у меня же есть CLI, зачем что-то ещё»). Модуль учит обратному: сначала
смотреть на задачу и людей вокруг неё, потом выбирать поверхность.

## Занятие 1. Поверхности использования

У Claude нет одного «правильного» интерфейса — есть четыре, и каждый закрывает
свой класс задач.

### Claude в Slack (Claude Tag)

Claude Tag — установка Claude прямо в Slack-workspace команды через
`/install-slack-app` (нужны права администратора workspace). После установки
Claude вызывается упоминанием (`@Claude`) в канале или треде. Типичные
сценарии: **сводка треда** — обсуждение на 40 сообщений превращается в 5
пунктов с решением и открытыми вопросами; **ответ на вопрос по каналу** —
Claude видит историю канала и отвечает новичку, не отвлекая живых людей;
**быстрый черновик** текста или проверка факта прямо во время обсуждения.

Ключевое ограничение: Claude Tag настроен на разговорный, короткий формат
ответа в рамках канала или треда. Это не место для многошагового рефакторинга
или длинных агентных пайплайнов — как только сценарий выходит за пределы
«прочитать контекст → дать текстовый ответ», это сигнал переключиться на CLI.

### IDE-расширения (VS Code, JetBrains)

Расширение Claude Code для VS Code или JetBrains (IntelliJ, PyCharm, WebStorm) —
не «CLI в другом окне», а интеграция с контекстом редактора: Claude видит
открытый файл, выделение, диагностику линтера, показывает инлайн-предложения
прямо у курсора и предлагает правки как diff-review внутри IDE. Между VS Code
и JetBrains принципиальной разницы в возможностях нет — важно, где уже живёт
команда: если репозиторий открыт в PyCharm, ставить рядом VS Code не нужно.

| | CLI (терминал) | IDE-расширение |
|---|---|---|
| Контекст редактора | нужно указывать явно (пути, строки) | видит открытый файл и курсор автоматически |
| Формат правок | диффы в терминале | инлайн-предложения, встроенный diff-viewer |
| Удобно для | больших многофайловых задач, автоматизации | точечных правок «здесь и сейчас» |
| Работа без человека за клавиатурой | да (headless, cron) | нет — нужна открытая IDE-сессия |

### Desktop / Web / CLI

- **Claude Desktop** — приложение на компьютере, локальный доступ к файлам и
  MCP-серверам машины. Профиль: личная продуктивность одного человека.
- **Claude Web (claude.ai)** — браузерный доступ без установки, артефакты,
  проекты с общими файлами. Профиль: быстрый доступ с любого устройства.
- **Claude CLI (Claude Code)** — терминальный инструмент для кодовой базы и
  автоматизации. Профиль: разработка, headless-запуски, scheduled tasks, CI.

Практическое правило: задача про **написание и обслуживание кода** — CLI или
IDE-расширение; про **личную продуктивность и разовые артефакты** — Desktop
или Web; про **общение с командой в реальном времени** — Slack. Один и тот же
человек за день обычно проходит все поверхности по очереди: Slack с утра,
IDE и CLI днём, Web или Desktop — для сводки к вечеру. Задача не выбрать одну
поверхность навсегда, а для каждой задачи выбирать её осознанно.

### Практика

Сопоставьте 4 реальных сценария вашей команды с подходящей поверхностью.
Пример разбора:

| Сценарий команды | Поверхность | Почему |
|---|---|---|
| Быстрый вопрос на созвоне («что означает этот код ошибки?») | Slack (Claude Tag) | ответ нужен в канале, без переключения контекста |
| Рефакторинг сервиса на 30 файлов | CLI | полный доступ к репозиторию, git, тесты, headless-режим |
| Точечная правка функции во время написания кода | IDE-расширение | Claude уже видит открытый файл и курсор |
| Разовый сводный отчёт по метрикам для встречи | Web / Desktop | не требует репозитория, удобно приложить файлы |

Сделайте такую же таблицу для своей команды. Хороший признак осознанного
выбора — если хотя бы одна строка оказалась неожиданной для вас самих. Если
все четыре указывают на одну поверхность, вероятно, сценарии взяты слишком
однотипно — возьмите задачи из разных частей рабочего дня.

## Занятие 2. MCP-реестр и подбор интеграций

### Зачем реестр, если можно написать свой сервер

В Модуле 2 вы уже писали собственный MCP-сервер — важный навык, но не всегда
нужный. Если задача — «подключить Claude к Google Drive» или «дать доступ к
Linear», почти наверняка кто-то уже опубликовал такой коннектор. Реестр
MCP-коннекторов — каталог готовых интеграций: поиск по сервису или задаче,
просмотр запрашиваемых прав, подключение в несколько кликов вместо нескольких
дней разработки.

Правило по умолчанию: **сначала ищем в реестре, пишем свой сервер только
если готового решения нет или оно не проходит проверку безопасности**. Чужой
поддерживаемый коннектор обновляется без вашего участия, свой сервер придётся
чинить самим при каждом изменении API стороннего сервиса. Обратная сторона:
свой сервер даёт полный контроль, а готовый коннектор — чужой код, которому
команда доверяет без построчного ревью. Поэтому подбор из реестра не отменяет
проверку, а переносит её с «читать код» на «читать список прав и репутацию
издателя».

### Пример: от задачи команды к коннектору

| Команде нужно | Использовать | Комментарий |
|---|---|---|
| Подтягивать тикеты и обновлять их статус | Коннектор к трекеру задач (Linear, Jira) | проверить: разрешена ли запись статуса или только чтение |
| Доступ к рабочим документам компании | Коннектор к облачному хранилищу (Google Drive) | обычно OAuth от имени пользователя — доступ не шире его прав |
| Автоматизировать код-ревью PR | Коннектор к GitHub/GitLab | чтение репозитория vs запись комментариев vs слияние веток |
| Регулярный отчёт в командный чат | Коннектор к Slack + scheduled task (Модуль 2) | здесь же проверяется headless-совместимость |

### Критерии выбора коннектора

Перед подключением команда отвечает на три вопроса:

1. **Авторизация.** OAuth от имени пользователя, сервисный токен, API-ключ?
   От этого зависит, чьими правами действует Claude и что случится при утечке.
2. **Ограничения безопасности.** Только чтение или ещё запись/удаление?
   Совпадает ли объём прав с реальной потребностью задачи, или коннектор
   просит больше «на всякий случай»?
3. **Headless-совместимость.** Будет ли коннектор работать в cron-задаче,
   scheduled task, ночном прогоне без человека? Часть коннекторов интерактивна
   по конструкции (например, требует подтверждения в браузере) и в headless-
   сценарии просто зависнет — это проверяется **до**, а не после первого сбоя.

### Настройка интеграции: пошагово

1. Сформулировать задачу одним предложением («агент должен читать новые
   тикеты из Linear и писать сводку в Slack»).
2. Найти в реестре коннектор(ы) под каждую часть задачи.
3. Прочитать список запрашиваемых прав до подключения, не после.
4. Подключить в тестовом окружении и проверить один реальный сценарий вручную.
5. Только после проверки — подключать туда, где агент работает регулярно, и
   зафиксировать, какие права выданы и кем одобрены.

### Практика

Найдите в реестре 1–2 коннектора под реальную задачу вашей команды. Для
каждого зафиксируйте: какие права он запрашивает; уместен ли этот объём для
задачи (и если нет — что избыточно); будет ли он работать headless, если
сценарий это предполагает.

## Итоговый проект модуля

Настройте (или, если нет административного доступа, детально спроектируйте)
одну реальную интеграцию Claude в рабочий процесс вашей команды — как
сравнение «до / после»:

- **Было**: как задача решалась без Claude — с какими издержками (время,
  ошибки, задержка).
- **Стало**: какая поверхность выбрана и какой коннектор подключён, с
  обоснованием по критериям выше.
- **Права доступа**: что выдано и почему этого достаточно (принцип
  минимально необходимых прав, а не «на всякий случай»).
- **Headless-проверка**: если интеграция должна работать без участия
  человека — подтверждение, что это действительно так.

Пример готового результата (сокращённо): команда еженедельно вручную
собирала статус спринта из трёх источников и тратила на это час утром в
понедельник. Решение: коннектор к трекеру задач (только чтение одного
проекта) плюс Claude Tag в канале спринта, который раз в неделю по scheduled
task собирает и публикует сводку. Headless-проверка пройдена — сводка
приходит без ручного вызова. Час ручной работы заменён на пять минут
проверки готового текста.

Если административного доступа к нужному сервису нет, детальное
проектирование засчитывается наравне с реальной настройкой: важно показать
решение на уровне поверхности, коннектора и прав доступа, а не общую идею
«подключить Claude к чему-нибудь».

## Критерии проверки

- [ ] Выбранная поверхность использования соответствует характеру задачи
- [ ] Для выбранного коннектора можно объяснить, какие права он запрашивает
- [ ] Учтено, будет ли интеграция работать в headless/автоматическом режиме,
      если это требуется сценарием
- [ ] Есть явное сравнение «было / стало» с измеримой или хотя бы
      описываемой разницей
- [ ] Права доступа задокументированы и обоснованы принципом минимальной
      достаточности
