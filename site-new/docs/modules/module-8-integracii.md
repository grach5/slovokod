Вы уже умеете работать с Claude Code, MCP-серверами и агентами. Осталось встроить Claude в рабочий процесс команды, а не только в свой терминал: выбирать поверхность под задачу, а не тащить один инструмент во все сценарии.

## Занятие 1. Поверхности использования

У Claude четыре поверхности, каждая закрывает свой класс задач.

### Claude в Slack (Claude Tag)

Устанавливается в workspace через `/install-slack-app` (нужны права администратора), вызывается упоминанием `@Claude`.

- **Сводка треда**: 40 сообщений → 5 пунктов с решением и открытыми вопросами.
- **Ответ на вопрос в канале** — без отвлечения живых людей.
- **Быстрый черновик** или проверка факта прямо в обсуждении.

Формат разговорный и короткий. Сценарий сложнее «прочитать контекст → ответить» — сигнал переключиться на CLI.

### IDE-расширения (VS Code, JetBrains)

Не «CLI в другом окне», а интеграция с контекстом редактора: видит открытый файл, курсор, диагностику линтера, предлагает правки инлайн.

| | CLI | IDE-расширение |
|---|---|---|
| Контекст | указывается явно | видит файл и курсор сам |
| Правки | диффы в терминале | инлайн, встроенный diff-viewer |
| Хорошо для | многофайловых задач, автоматизации | точечных правок |
| Headless (без человека) | да | нет |

### Desktop / Web / CLI

- **Desktop** — локальный доступ к файлам и MCP машины. Личная продуктивность.
- **Web (claude.ai)** — без установки, артефакты, общие проекты. Доступ с любого устройства.
- **CLI (Claude Code)** — терминал, headless-запуски, scheduled tasks, CI.

Правило: код → CLI/IDE; личные разовые задачи → Desktop/Web; реальное время с командой → Slack.

### Практика

Сопоставьте 4 сценария команды с поверхностью:

| Сценарий | Поверхность | Почему |
|---|---|---|
| Вопрос на созвоне про код ошибки | Slack | ответ в канале, без переключения |
| Рефакторинг сервиса на 30 файлов | CLI | репозиторий, git, тесты, headless |
| Точечная правка функции | IDE | Claude уже видит файл и курсор |
| Разовый отчёт по метрикам | Web/Desktop | не требует репозитория |

Хороший признак осознанного выбора — если хоть одна строка вашей таблицы вас удивила.

## Занятие 2. MCP-реестр и подбор интеграций

### Зачем реестр, если можно написать свой сервер

Для типовых задач («подключить Google Drive», «доступ к Linear») готовый коннектор почти наверняка уже есть в реестре MCP.

Правило по умолчанию: сначала реестр, свой сервер — только если готового решения нет или оно не проходит проверку безопасности. Чужой коннектор обновляется без вас; свой придётся чинить самим. Плата за готовое — доверие чужому коду без построчного ревью, поэтому проверка смещается на права и репутацию издателя.

### Пример: от задачи к коннектору

| Нужно | Коннектор | Проверить |
|---|---|---|
| Тикеты и статусы | Трекер задач (Linear, Jira) | запись статуса или только чтение |
| Рабочие документы | Облако (Google Drive) | OAuth от пользователя — не шире его прав |
| Код-ревью PR | GitHub/GitLab | чтение vs комментарии vs слияние веток |
| Отчёт в чат | Slack + scheduled task | headless-совместимость |

### Критерии выбора коннектора

- **Авторизация** — OAuth от пользователя, сервисный токен или API-ключ: чьими правами действует Claude.
- **Безопасность** — только чтение или ещё запись/удаление; объём прав по потребности, не «на всякий случай».
- **Headless** — работает ли без человека в cron/scheduled task, или требует ручного подтверждения (проверить до подключения).

### Настройка интеграции: пошагово

1. Задача одним предложением («агент читает тикеты из Linear, пишет сводку в Slack»).
2. Найти коннектор под каждую часть задачи в реестре.
3. Прочитать список прав до подключения.
4. Проверить один сценарий вручную в тестовом окружении.
5. Подключить к регулярной работе, зафиксировав выданные права.

### Практика

Найдите 1–2 коннектора под задачу команды. Зафиксируйте: права, их уместность, headless-совместимость.

## Итоговый проект модуля

Настройте (или детально спроектируйте без доступа) одну интеграцию Claude в рабочий процесс команды:

- **Было** — издержки без Claude (время, ошибки, задержка).
- **Стало** — поверхность и коннектор с обоснованием.
- **Права** — что выдано и почему этого достаточно.
- **Headless-проверка** — если нужно, подтверждение, что работает без человека.

Пример: сборка статуса спринта из трёх источников занимала час по понедельникам. Решение — коннектор к трекеру (только чтение) плюс Claude Tag со scheduled task раз в неделю. Час ручной работы → пять минут проверки текста.

Без административного доступа проектирование засчитывается наравне с настройкой — важно показать решение на уровне поверхности, коннектора и прав, а не общую идею.

## Критерии проверки

- [ ] Поверхность соответствует характеру задачи
- [ ] Понятно, какие права запрашивает коннектор
- [ ] Учтена headless-совместимость, если она нужна сценарием
- [ ] Есть сравнение «было / стало» с конкретной разницей
- [ ] Права задокументированы по принципу минимальной достаточности
