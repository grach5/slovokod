## Зачем это

Вы отправили ассистенту всё техническое задание (ТЗ — документ с описанием задачи) одним запросом.
Получили результат: половина работает, половина нет.
Начали чинить вторую половину — сломалась первая.
Дело не в объёме задания. Дело в том, что вы попросили сразу много всего.
Сегодня вы научитесь резать задачу на части, которые проверяются по одной.

## Что вы сделаете

Разобьёте своё ТЗ на 5-7 шагов и соберёте первый рабочий шаг проекта.

## Главное правило

**Шаг считается правильным, если после него можно нажать «проверить» и получить однозначный ответ «работает» или «нет».** Если проверить нельзя — это не шаг, а пожелание. «Сделать красиво» проверить нельзя. «Показать список из трёх услуг» — можно: список либо есть на экране, либо его нет.

## Теория

Есть порядок, в котором части проекта собираются без потерь.

1. Каркас — экраны и переходы между ними. Пока без реальных данных, с выдуманным содержимым для примера.
2. Действия — что происходит при нажатии на кнопку или ссылку.
3. Данные — что сохраняется и откуда берётся при следующем открытии.
4. Внешний вид — цвета, отступы, шрифты.

Начать хочется с внешнего вида: результат сразу видно, это приятно. Но соблазн обманчив. Каждая правка каркаса после этого ломает оформление — кнопка съезжает, текст не помещается. Оформление приходится переделывать заново, обычно несколько раз.

Отличить хороший шаг от плохого просто: «сделать запись клиентов» одним действием не проверяется — неясно, что именно должно появиться на экране. «Показать список из трёх услуг с ценами» проверяется — вы либо видите три строки с ценами, либо нет.

Действует правило одного изменения: в одном запросе к ассистенту — одно изменение. Если отправить два изменения сразу и что-то сломается, вы не поймёте, какое из них виновато. Одно изменение — одна проверка — один понятный результат.

## По шагам

1. Откройте своё ТЗ и найдите блок 3 («что человек видит и делает по шагам»).
   Вы должны увидеть: список шагов пользователя, написанный вами на дне 2.

2. Выпишите каждый шаг пользователя отдельной строкой в новый файл.
   Вы должны увидеть: список строк, под каждой есть свободное место.

3. Под каждой строкой запишите, что именно должно появиться на экране после этого шага.
   Вы должны увидеть: под каждой строкой — конкретное описание того, что видно глазами.

4. Вычеркните пункты, которые нельзя проверить одним действием.
   Вы должны увидеть: часть строк вычеркнута, остальные звучат как проверяемый факт.

5. Расставьте оставшиеся пункты в порядке каркас → действия → данные → вид.
   Вы должны увидеть: список, где сначала экраны, потом нажатия, потом сохранение данных, потом оформление.

6. Пронумеруйте пункты. Если получилось больше 10 — объедините мелкие. Если меньше 4 — режьте крупные дальше.
   Вы должны увидеть: пронумерованный список из 5-7 пунктов.

7. Возьмите пункт 1 и отправьте на него промт ассистенту.
   Вы должны увидеть: ответ ассистента с готовым кодом для первого шага.

8. Проверьте результат по критерию, который вы написали в пункте 3 для шага 1.
   Вы должны увидеть: совпадение того, что на экране, с тем, что вы описали — либо расхождение.

9. Не переходите к шагу 2, пока шаг 1 не прошёл проверку.
   Вы должны увидеть: рядом с пунктом 1 в вашем списке — отметка «проверено».

## Готово к копированию

Файл Шаги.md — шаблон для разбивки задачи:

```
ШАГИ ПРОЕКТА

Шаг 1: [каркас — что за экран]
Готово, когда на экране видно: [конкретный признак]

Шаг 2: [каркас или действия]
Готово, когда на экране видно: [конкретный признак]

Шаг 3: [действия]
Готово, когда на экране видно: [конкретный признак]

Шаг 4: [данные]
Готово, когда на экране видно: [конкретный признак]

Шаг 5: [данные или вид]
Готово, когда на экране видно: [конкретный признак]
```

Промт для сборки одного шага — отправьте вместе с описанием шага:

```
Мы собираем проект по шагам. Ниже общее описание проекта — оно нужно тебе
только для понимания направления.

[блоки 1-2 из ТЗ]

Сейчас сделай ТОЛЬКО ЭТО: [текст шага 1].

Готово считается так: [критерий из пункта 3].

Ограничения: не добавляй ничего сверх описанного, не улучшай оформление,
не добавляй функции на будущее. Выдай готовый код одним блоком.
```

## Типичные ошибки

- Шагов получилось два, каждый огромный → резать по проверяемости, не по смыслу.
- Начали с оформления → верните пункт про внешний вид в конец списка.
- Отправили всё ТЗ разом → результат наполовину рабочий → начните заново с шага 1, разбирать выданное дороже, чем пересобрать.
- Проверяете «на глаз, вроде норм» → критерий не был сформулирован заранее → пишите критерий до запроса, а не после ответа.
- Просите «а ещё заодно поменяй кнопку» → нарушено правило одного изменения → оформите это отдельным шагом.

## Задание и критерии приёмки

- [ ] Список шагов состоит из 5-7 пунктов
- [ ] У каждого пункта есть критерий «готово, когда на экране видно…»
- [ ] Порядок пунктов: каркас → действия → данные → вид
- [ ] Ни один пункт не содержит слов «удобно», «красиво», «нормально», «правильно»
- [ ] Файл Шаги.md сохранён
- [ ] Первый шаг отправлен ассистенту и получен код
- [ ] Первый шаг проверен по своему критерию
- [ ] Оформлением сегодня не занимались

## Если не получилось

- Не выходит сформулировать критерий → шаг слишком абстрактный, спросите себя: что вы увидите на экране, чего не видели раньше?
- Ассистент делает больше, чем просили → повторите ограничение в запросе, добавьте: «если хочешь предложить что-то ещё — перечисли, но не делай».
- Первый шаг не работает → не переходите дальше, опишите ассистенту одним сообщением, что видите и что ожидали увидеть.
- Список получился на 15 пунктов → объедините всё, что происходит на одном экране, в один пункт.
