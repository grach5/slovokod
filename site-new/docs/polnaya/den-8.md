## Зачем это

До сегодня проект существовал только у вас на компьютере. Показать его можно было только через скриншот.
Сегодня появится ссылка — можно отправить кому угодно, открыть с телефона, положить в резюме.
Работодателю или заказчику не нужен ваш ноутбук — нужен адрес в интернете.
Без публикации проект остаётся черновиком, который никто, кроме вас, не видел.

## Что вы сделаете

Опубликуете проект в интернете и проверите, что правки появляются на сайте автоматически.
Результат: рабочая ссылка, которая обновляется сама после каждой отправленной точки на GitHub.

## Главное правило

**Публикация делается из репозитория, а не с вашего компьютера.** Сервис публикации берёт код с GitHub, а не с диска. Каждая отправленная на GitHub точка (commit) обновляет сайт автоматически — заново отправлять файлы вручную не нужно.

## Теория

Схема публикации простая: папка на компьютере → GitHub → сервис публикации → адрес в интернете.

Сервис публикации — это программа, которая следит за вашим репозиторием на GitHub. Как только там появляется новая точка, сервис забирает код, собирает сайт и выкладывает его по своему адресу. Обновление автоматическое: отправили точку — сайт обновился сам, обычно за минуту. В этом дне используется Vercel (vercel.com) — заходите через кнопку «Continue with GitHub», отдельный пароль не нужен.

Бесплатного тарифа таких сервисов хватает учебному проекту и первым заказам, с запасом. Платить за это на старте не нужно.

Адрес сайта сначала будет техническим — вида `имя-проекта.вашсервис.app`. Свой домен (например `mysite.ru`) можно подключить позже, это отдельная, платная услуга. Спешить с ним не нужно: сначала проект должен просто заработать.

Ошибка при первой публикации — это нормально, а не признак того, что вы что-то сломали. Первая попытка часто падает из-за мелочей: не той версии, лишнего файла, забытой настройки. Сервис показывает журнал (log) — текст с описанием, что пошло не так. Этот текст нужно скопировать целиком и отдать ассистенту — он по тексту ошибки точно скажет, в чём дело.

Дальше — пошаговая инструкция, как пройти публикацию в первый раз и что делать, если она не удалась.

## По шагам

1. Откройте vercel.com в браузере.
   Вы должны увидеть: страницу входа с кнопкой «Continue with GitHub».

2. Зарегистрируйтесь через свой аккаунт GitHub (не заводите новый пароль отдельно).
   Вы должны увидеть: вы вошли в сервис, виден список ваших репозиториев.

3. Выберите из списка репозиторий вашего проекта.
   Вы должны увидеть: страницу настройки публикации с именем вашего репозитория.

4. Оставьте настройки по умолчанию — менять их не нужно, значения почти всегда верны.
   Вы должны увидеть: кнопку запуска публикации (Deploy).

5. Запустите публикацию и дождитесь окончания.
   Вы должны увидеть: сообщение об успехе или сообщение об ошибке.

6. Если публикация упала — откройте журнал, скопируйте текст ошибки целиком и отдайте ассистенту промтом из блока ниже.
   Вы должны увидеть: от ассистента — причину ошибки одной строкой и точный список действий.

7. Когда публикация прошла успешно, откройте полученный адрес в браузере на компьютере.
   Вы должны увидеть: ваш проект открылся по адресу вида `имя-проекта.вашсервис.app`.

8. Отправьте себе ссылку в мессенджер и откройте её с телефона.
   Вы должны увидеть: тот же проект, открытый на экране телефона.

9. Внесите в проект небольшую правку, сохраните файл, отправьте точку на GitHub.
   Вы должны увидеть: в GitHub — новую точку в истории репозитория.

10. Подождите минуту и обновите страницу сайта в браузере.
    Вы должны увидеть: правка появилась на сайте без каких-либо ручных действий с вашей стороны.

## Готово к копированию

```
Публикация проекта не удалась. Вот текст ошибки из журнала целиком: [вставить полностью, не сокращая]. Скажи одной строкой, в чём причина, и дай точный список действий. Не предлагай менять то, что не относится к этой ошибке.
```

## Типичные ошибки

- Правки не появляются на сайте → точка не отправлена на GitHub, сайт берёт код оттуда, не с диска → отправьте точку на GitHub и подождите минуту.
- На телефоне разъезжается вёрстка → проверяли только на широком экране компьютера → попросите ассистента адаптировать страницу под маленький экран.
- Чините публикацию, меняя настройки наугад → причина не найдена, вы просто перебираете варианты → откройте журнал, там написана точная причина.
- Сайт открывается пустым → возможна ошибка в коде, которая видна только в браузере → нажмите F12, откройте вкладку Console, посмотрите красные строки.
- Сразу покупаете свой домен → это преждевременный расход → отложите покупку, сначала убедитесь, что сайт работает на техническом адресе.

## Задание и критерии приёмки

- [ ] Проект опубликован, есть рабочая ссылка.
- [ ] Ссылка открывается с чужого устройства.
- [ ] Страница корректно выглядит на телефоне.
- [ ] Правка, отправленная на GitHub, появилась на сайте без ручных действий.
- [ ] Вы можете назвать, где смотреть журнал ошибок публикации.
- [ ] В репозитории по-прежнему нет файла `.env`.

## Если не получилось

- Публикация падает третий раз подряд → отдайте ассистенту сразу три вещи: текст ошибки целиком, содержимое файла `package.json`, список файлов в корне репозитория.
- Сервис не видит ваш репозиторий → проверьте, что вошли в сервис тем же аккаунтом GitHub, где лежит проект, и дали сервису доступ к репозиториям.
- Сайт работает на компьютере, но не в интернете → почти всегда причина в отсутствующих переменных окружения (environment variables) — их нужно завести отдельно в настройках сервиса, подробнее об этом — завтра.
- Не можете найти журнал ошибок → в панели сервиса публикации ищите раздел с названием вроде Deploy Logs или Build Logs, обычно рядом со статусом последней публикации.
