## Зачем это

Вчера у вас появился первый ключ доступа.
С этого момента проект стоит денег и содержит чужие данные.
Утечка выглядит не как взлом из фильма — как счёт на сумму, которую вы не тратили, или база клиентов у постороннего.
И происходит почти всегда одинаково: ключ попал в публичный репозиторий (место, где хранится код проекта).

## Что вы сделаете

Проверите проект на утечки секретов, разложите ключи по правильным местам и заведёте менеджер паролей.

## Главное правило

**Ключ, попавший в репозиторий хотя бы на минуту, считается скомпрометированным навсегда. Публичные репозитории сканируются автоматически, удаление файла не помогает — ключ остаётся в истории изменений.**

## Теория

Секрет — это ключ доступа, пароль от базы, токен (код доступа сервиса) или код платёжной системы. Всё, что даёт возможность действовать от вашего имени.

Три места, где секреты хранить правильно:
- файл `.env` на компьютере — для локальной разработки;
- настройки сервиса публикации — для работающего сайта;
- менеджер паролей — личный архив всех доступов.

Три места, где секретов быть не должно:
- код;
- репозиторий;
- переписка с ассистентом.

Последний пункт неочевиден. Вставляя в чат код с настоящим ключом, вы отправляете этот ключ третьей стороне. Перед отправкой заменяйте ключ на заглушку, например `ВАШ_КЛЮЧ`.

Некоторые сервисы выдают два ключа: публичный и приватный (секретный). Их обязательно различать — публичный можно показывать, приватный нет. Если не уверены, какой из двух перед вами, — считайте секретным.

Дальше вы пройдёте по проекту с этим знанием и наведёте порядок.

## По шагам

1. Откройте репозиторий на GitHub (сайт github.com, не программа на компьютере — та же ссылка, что открывалась в Дне 6 по кнопке из GitHub Desktop). Нажмите на строку поиска в верхней панели GitHub, впишите слово key и нажмите Enter — откроется вкладка Code с результатами; повторите для secret, password, token. Вы должны увидеть: список файлов, где встречаются эти слова, или пустой результат.

2. Просмотрите историю коммитов (точек сохранения изменений) — не мелькали ли в ней лишние файлы с настоящими ключами. Вы должны увидеть: список коммитов без файлов вроде `.env` или конфигов с ключами.

3. Убедитесь, что файл `.gitignore` содержит строки `.env`, `node_modules`, `.DS_Store`. Вы должны увидеть: эти три строки в файле `.gitignore`.

4. Создайте файл `.env.example` с теми же переменными, что в `.env`, но со значениями-заглушками. Вы должны увидеть: файл `.env.example` с именами переменных и словами вроде `ваш_ключ_сюда` вместо значений.

5. Проверьте, что `.env.example` попал в репозиторий, а `.env` — нет. Вы должны увидеть: `.env.example` в списке файлов на GitHub, `.env` в этом списке отсутствует.

6. Откройте настройки сервиса публикации сайта и убедитесь, что там прописаны те же переменные с реальными значениями. Вы должны увидеть: список переменных окружения, заполненных в панели сервиса.

7. Пройдите по коду проекта и убедитесь, что нигде не осталось строки с настоящим ключом. Было: `const apiKey = "sk-abc123realkey"`. Стало: `const apiKey = process.env.API_KEY` — имя переменной (`API_KEY`) вы пишете сами в коде, а настоящее значение лежит только в `.env` и в панели сервиса публикации (уже сделано в шагах 4–6), код подставляет его сам при запуске. Вы должны увидеть: во всех местах, где раньше был ключ, теперь стоит обращение к переменной окружения.

8. Если на шаге 1 или 2 нашли утечку — выполните порядок действий из блока «Готово к копированию» ниже, строго по пунктам. Вы должны увидеть: новый ключ работает, старый отозван.

9. Заведите менеджер паролей и сложите туда все доступы проекта: логины, ключи, пароли от сервисов. Вы должны увидеть: в менеджере паролей есть запись на каждый сервис, которым вы пользуетесь в проекте.

## Готово к копированию

```
Проверь проект на секреты в коде. Перечисли файлы и строки, где встречаются ключи, пароли, токены или строки подключения. Ничего не исправляй, просто дай список. Затем скажи, как вынести найденное в переменные окружения.
```

Порядок действий при обнаруженной утечке — строго по пунктам:

```
1. Зайти в сервис, выдавший ключ.
2. Отозвать или перевыпустить ключ — это первое и самое срочное действие.
3. Прописать новый ключ в .env и в настройках сервиса публикации.
4. Добавить .env в .gitignore, если он там ещё не значится.
5. Проверить, что новый ключ никуда не попал — ни в код, ни в чат.
6. Проверить журнал использования сервиса — не было ли чужих обращений по старому ключу.
```

## Типичные ошибки

- «Репозиторий приватный, значит можно» → приватный репозиторий становится публичным одним неверным нажатием → храните ключи так, будто репозиторий уже публичный.
- Удалили файл с ключом и успокоились → ключ остался в истории коммитов → всё равно перевыпускайте ключ.
- Вставили в чат ассистенту код вместе с настоящими ключами → ассистент увидел ключ, это утечка третьей стороне → заменяйте ключ на `ВАШ_КЛЮЧ` перед отправкой.
- Один ключ используется во всех сервисах → утечка одного ключа открывает доступ ко всему → заводите разные ключи для разных сервисов.
- Ключи и пароли хранятся в заметках телефона → заметки не защищены и синхронизируются в облако без вашего контроля → перенесите всё в менеджер паролей.

## Задание и критерии приёмки

- [ ] Поиск по репозиторию не находит настоящих ключей.
- [ ] Файл `.gitignore` содержит `.env`.
- [ ] Есть файл `.env.example` с заглушками вместо значений.
- [ ] Переменные окружения прописаны в настройках сервиса публикации.
- [ ] Все доступы перенесены в менеджер паролей.
- [ ] Вы можете назвать порядок действий при утечке ключа, не подглядывая.

Сдаёте: скриншот результата поиска по репозиторию и содержимое `.env.example`.

## Если не получилось

- Не понимаете, какие ключи вообще есть в проекте → зайдите в каждый сервис, которым пользуетесь, и найдите там раздел с ключами доступа.
- После выноса ключей в переменные проект перестал работать → переменные не подхватываются кодом → отдайте ассистенту файл `.env.example` и текст ошибки.
- Ключ утёк, а сервис не даёт его перевыпустить → удалите проект в этом сервисе и создайте заново → это дешевле любых последствий утечки.
