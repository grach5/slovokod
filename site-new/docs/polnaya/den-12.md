## Зачем это

Проект собрался быстро — и, скорее всего, в нём остались одни и те же дыры.
Не потому что вы сделали что-то не так: ассистент оптимизирует под «работает», а не под «безопасно».
Пока проект видите только вы, это неважно.
В день, когда даёте ссылку клиенту, это становится вашей ответственностью.

## Что вы сделаете

Пройдёте чек-лист из 15 пунктов безопасности и закроете найденные дыры.

## Главное правило

**Ассистент не отвечает за безопасность вашего продукта. Отвечаете вы. Он не откажется сделать открытую всем базу — сделает то, о чём попросили.**

## Теория

Что ломается чаще всего:

- **Данные открыты на чтение** — самая частая и дорогая дыра. Таблица доступна кому угодно, у кого есть ссылка.
- **Нет проверки на стороне сервера.** Проверка в форме отсеивает честные ошибки, но обходится за минуту. Настоящая защита — там, куда данные приходят.
- **Нет ограничения на количество отправок.** Форма без лимита набирает десятки тысяч записей за ночь.
- **Технические ошибки видны пользователю.** Сообщение с адресом базы — подарок постороннему.
- **Забытые тестовые данные.** Пользователь `test` с паролем `123` в рабочей версии.

Дальше — 15 пунктов подряд. По каждому — «да» или задача на исправление.

## По шагам

1. Ключей нет в коде и репозитории. Вы должны увидеть: ни один ключ не найден при поиске по проекту.
2. `.env` в `.gitignore`. Вы должны увидеть: строку `.env` в файле `.gitignore`.
3. Права доступа к базе: посторонний не читает записи. Не помните, через какой сервис делали базу? Откройте файл `.env` в проекте — адрес в нём обычно содержит имя сервиса (например, `supabase.co`); откройте этот адрес и войдите в свой аккаунт (или посмотрите в менеджере паролей из Дня 10). Вы должны увидеть: в настройках сервиса читать может только владелец.
4. Проверка данных не только в форме, но и на приёме. Вы должны увидеть: сервер отклоняет пустые обязательные поля, даже если отправить их напрямую.
5. Есть ограничение на частоту отправки с устройства. Вы должны увидеть: повторная отправка подряд блокируется или задерживается.
6. Ограничена длина текстовых полей. Вы должны увидеть: очень длинный текст обрезается или отклоняется.
7. Пользователю — человеческие сообщения об ошибках, без деталей. Вы должны увидеть: текст вроде «попробуйте ещё раз», а не адрес базы или код ошибки.
8. Тестовые записи и пользователи удалены. Вы должны увидеть: пустую или только настоящую таблицу.
9. Адрес сайта начинается с `https`. Вы должны увидеть: замок в адресной строке браузера.
10. Загрузка файлов ограничена по типу и размеру. Вы должны увидеть: попытка загрузить чужой тип файла отклоняется.
11. Нет страниц управления без входа по паролю. Админка — отдельная страница для управления данными сайта (например `/admin`), есть не в каждом проекте; спросите ассистента «есть ли в моём проекте страница администрирования и по какому адресу», затем откройте этот адрес в приватном окне браузера. Вы должны увидеть: адрес админки требует логин (или её вовсе нет в проекте — тоже нормально).
12. Есть резервная копия данных. Вы должны увидеть: выгрузку или снимок таблицы, сохранённый отдельно.
13. Проверено на телефоне. Вы должны увидеть: сайт открывается и работает на маленьком экране.
14. Проверено на пустых и очень длинных значениях. Вы должны увидеть: форма не ломается ни в одном из этих случаев.
15. Если собираются персональные данные — есть согласие и указано, кто и зачем их собирает. Вы должны увидеть: текст согласия рядом с формой.

## Готово к копированию

Если у ассистента есть прямой доступ к файлам проекта (агентный режим — тема Дня 13) — он сам укажет файл и строку. Если вы ещё работаете через обычный чат — вставьте в сообщение содержимое ключевых файлов проекта (`.env.example`, файлы с формами и запросами к базе), и ассистент ответит по тому, что видит.

## Типичные ошибки

- Чек-лист проходят «по памяти» → пункт кажется выполненным, но никто не проверял → проверяйте каждый пункт руками.
- Полагаются на ответ ассистента о правах доступа → ассистент не видит настройки сервиса → проверяйте права в самом сервисе базы.
- Проверяют только правильные данные → форма ломается на пустом поле или спецсимволах → тестируйте пустые и очень длинные значения.
- Исправляют всё разом → одна правка ломает другую, и непонятно, где именно → исправляйте по одному пункту с проверкой.
- Пропускают пункт 15 → сбор телефонов без согласия — не техническая мелочь → добавьте текст согласия рядом с формой.

## Задание и критерии приёмки

- [ ] Все 15 пунктов проверены руками.
- [ ] Права доступа проверены в самом сервисе базы данных.
- [ ] Проверка на пустых и длинных значениях выполнена по каждому полю.
- [ ] Тестовые данные удалены.
- [ ] Каждое исправление сделано отдельной точкой, с проверкой.
- [ ] Сайт после исправлений работает.

Сдаёте: заполненный чек-лист с отметками и список исправленного.

## Если не получилось

- Не понимаете пункт → попросите ассистента объяснить на примере вашего проекта и показать, где смотреть.
- Исправление ломает проект → откатите изменение, затем внесите меньшую правку.
- Пунктов «не выполнено» больше половины → это норма для первого проекта. Идите сверху вниз, начиная с доступа к данным.

- А) Ассистент
- Б) Сервис публикации
- В) Вы
- Г) Сервис базы данных

**2. Проверка данных в форме браузера:**
- А) Достаточна
- Б) Отсеивает честные ошибки, но обходится за минуту
- В) Не нужна
- Г) Заменяет проверку на сервере
<details><summary>Ответ</summary>Правильный: Б.</details>

**3. Форма без ограничения на частоту отправки:**
- А) Работает быстрее
- Б) Может набрать десятки тысяч записей за ночь
- В) Ничем не рискует
- Г) Защищена сервисом автоматически
<details><summary>Ответ</summary>Правильный: Б.</details>

**4. Пользователю при ошибке показывают:**
- А) Технические детали с адресом базы
- Б) Человеческое сообщение без технических деталей
- В) Пустой экран
- Г) Код ошибки
<details><summary>Ответ</summary>Правильный: Б.</details>

- Б) Должен быть удалён

- А) 5

**8. Права доступа к базе проверяют:**
- А) По ответу ассистента

**9. Собираете телефоны клиентов. На странице должно быть:**
