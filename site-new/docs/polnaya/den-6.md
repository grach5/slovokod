## Зачем это

Рано или поздно это случается с каждым. Вы просите правку, ассистент переписывает файл — и проект, работавший вчера, перестаёт работать.
Вернуть как было нельзя: прошлой версии просто больше нет.
Именно это чаще всего заставляет людей бросать проект на середине.
Сегодня вы устраните эту проблему полностью, за один день.

## Что вы сделаете

Настроите сохранение точек возврата для проекта и опубликуете его в GitHub — интернет-хранилище кода.
Проверите откат на практике: намеренно сломаете проект и вернёте его в рабочее состояние.

## Главное правило

**Точка возврата сохраняется перед каждой правкой, а не после.** Сохранить точку — десять секунд. Остаться без неё после поломки — потерянный вечер.

## Теория

Git — программа, которая запоминает состояния папки с проектом. Не отдельный файл, а весь проект целиком в конкретный момент: «вот так это выглядело в 14:30, и тогда всё работало».

Три действия с Git:

- **Сохранить точку** (это называется коммит) — Git запоминает состояние всех файлов проекта и подпись к этому состоянию.
- **Посмотреть историю** — список всех сохранённых точек с их подписями.
- **Откатиться** — вернуть файлы проекта к состоянию одной из точек.

GitHub — тот же Git, но в интернете. Это копия истории проекта на случай, если сломается ваш диск. Начиная с завтрашнего дня публикация сайта будет делаться именно из репозитория (хранилище кода на GitHub).

Есть жёсткое правило того, что нельзя выкладывать в репозиторий: всё, что туда попало, считается опубликованным навсегда. Даже если файл потом удалить, он останется в истории. Поэтому до самой первой точки настраивается файл `.gitignore` — список того, что Git должен игнорировать. Туда обязательно идут папка `node_modules` и файл `.env`.

Подписи к точкам важны. Плохая подпись — «правки» или «фикс». Хорошая — «работает форма записи»: подпись описывает состояние проекта, а не то, что вы сделали.

Сегодня вы работаете через GitHub Desktop — программу с окнами и кнопками, без единой команды в терминале. Если вы уже освоились с терминалом (День 5) и предпочитаете его — те же 15 шагов делаются командами git, они даны в блоке «Готово к копированию» ниже, вне основного пути.

## По шагам

1. Скачайте GitHub Desktop с сайта desktop.github.com и установите программу. Вы должны увидеть: программа открылась и просит войти в аккаунт.
2. Зарегистрируйтесь на github.com, если аккаунта ещё нет, и войдите в GitHub Desktop под этим аккаунтом. Вы должны увидеть: своё имя пользователя в углу программы.
3. Прежде чем сохранять первую точку, попросите ассистента создать `.gitignore` промтом из блока «Готово к копированию» ниже и сохраните файл в папку проекта. Вы должны увидеть: в папке проекта появился файл `.gitignore`.
4. В GitHub Desktop выберите File → Add local repository, укажите папку проекта и согласитесь создать репозиторий. Вы должны увидеть: список изменённых файлов слева.
5. Проверьте список файлов: в нём не должно быть тысяч файлов из `node_modules` и не должно быть файла `.env`. Вы должны увидеть: список из десятков файлов, а не тысяч. Если это не так — вернитесь к шагу 3 и проверьте содержимое `.gitignore`.
6. Напишите подпись «стартовая рабочая версия» в поле снизу слева и нажмите Commit to main (main — имя основной линии разработки, GitHub Desktop создаёт и называет её так сам, настраивать не нужно). Вы должны увидеть: список изменений опустел, точка сохранена.
7. Откройте вкладку History вверху окна. Вы должны увидеть: одну точку с подписью «стартовая рабочая версия».
8. Намеренно сломайте проект: откройте любой рабочий файл, удалите половину текста, сохраните файл. Убедитесь, что проект перестал работать. Вы должны увидеть: ошибку в браузере или в терминале при запуске проекта.
9. В GitHub Desktop откройте Changes, нажмите правой кнопкой по изменённому файлу и выберите Discard all changes. Вы должны увидеть: файл вернулся к прежнему виду.
10. Проверьте проект заново. Вы должны увидеть: проект снова работает, как до поломки.
11. Сделайте через ассистента три реальные правки проекта одну за другой. После каждой правки проверьте, что проект работает, и сохраните отдельную точку со своей подписью. Вы должны увидеть: во вкладке History — четыре точки, включая стартовую.
12. Нажмите Publish repository. Оставьте репозиторий публичным — так любой сможет открыть ссылку на код (`.env` и личные данные туда не попадут благодаря `.gitignore`), а вы сможете показать его в портфолио (подборке ваших проектов — показывать прямо сейчас никому не обязательно, пригодится позже). Вы должны увидеть: кнопка сменилась на Fetch origin или View on GitHub (origin — стандартное техническое имя ссылки на ваш репозиторий на GitHub, одинаковое у всех проектов, не название вашего аккаунта).
13. Попросите ассистента написать README (файл-описание проекта) промтом из блока «Готово к копированию» ниже и сохраните ответ как файл `README.md` в папку проекта. Вы должны увидеть: в папке проекта появился файл `README.md`.
14. Сохраните точку с подписью «добавлено описание» и нажмите Push origin. Вы должны увидеть: кнопка Push origin исчезла или показывает «0» изменений для отправки.
15. Откройте репозиторий в браузере по ссылке из GitHub Desktop. Вы должны увидеть: текст README на главной странице репозитория, и что в списке файлов нет `.env` и нет `node_modules`.

## Готово к копированию

```
Создай файл .gitignore для моего проекта. Обязательно включи: node_modules, .env, .DS_Store, папки сборки, файлы редакторов. Выдай только содержимое файла.
```

```
Напиши README для моего учебного проекта. Структура: название и одно предложение о продукте, для кого, что умеет (3-5 пунктов), как запустить (команды по порядку), чем сделано. Коротко, без воды, без эмодзи. Формат Markdown. Описание проекта: [вставить файл проекта]
```

:::tip[Те же 15 шагов через терминал вместо GitHub Desktop]
Если предпочитаете командную строку — тот же результат командами git (выполняются в папке проекта):

```bash
git init
# создать .gitignore промтом выше, затем:
git add .gitignore
git commit -m "gitignore"
git add -A
git commit -m "стартовая рабочая версия"
# на github.com создать пустой репозиторий, затем:
git remote add origin <ссылка на ваш репозиторий>
git branch -M main
git push -u origin main
# после каждой новой правки:
git add -A
git commit -m "<подпись, описывающая состояние>"
git push
```

`git status` показывает список изменённых файлов (аналог панели Changes), `git log --oneline` — историю точек (аналог вкладки History). Откат к точке — `git checkout -- .` для несохранённых изменений или `git reset --hard <хэш коммита>` для возврата к конкретной точке (хэш коммита — тот код из букв и цифр, что стоит первым в каждой строке `git log --oneline`; скопируйте его оттуда, ничего запоминать или придумывать не нужно). Осторожно: `--hard` необратимо удаляет несохранённые изменения, как и Discard all changes в GitHub Desktop.
:::

## Типичные ошибки

- Точка сохраняется после поломки → откатываться уже некуда → правило: коммит делается до правки, а не после.
- Подписи вида «фикс, ещё фикс» → через день непонятно, к какой точке возвращаться → подпись описывает состояние, а не действие.
- Один коммит в день → откат отменяет всю дневную работу целиком → сохраняйте точку после каждой проверенной правки.
- `.gitignore` создан после первого коммита → `node_modules` и `.env` уже попали в историю, простое удаление файла не помогает → нужно пересоздавать репозиторий с чистой историей.
- Точки сделаны, а на GitHub их нет → не нажата кнопка Push origin, синхронизация с интернетом не происходит автоматически → нажмите Push origin вручную.
- Discard all changes нажат по ошибке → несохранённые изменения удаляются без возможности вернуть → это единственная опасная кнопка в сегодняшнем уроке, используйте её осознанно.

## Задание и критерии приёмки

- [ ] Настроено отслеживание изменений проекта через Git
- [ ] Сделано не менее 5 точек, каждая подпись описывает состояние проекта
- [ ] В проекте есть `.gitignore`, включающий `node_modules` и `.env`
- [ ] В самом репозитории нет `.env` и нет `node_modules`
- [ ] В репозитории есть `README.md` с описанием, возможностями и инструкцией запуска
- [ ] Вы намеренно сломали проект и восстановили его откатом
- [ ] Вы можете объяснить своими словами, что делает Discard all changes
- [ ] В тестовых данных проекта нет настоящих имён и телефонов

## Если не получилось

- `.env` уже попал в историю репозитория → считайте все ключи из него скомпрометированными → порядок действий: перевыпустить ключи, добавить `.env` в `.gitignore`, удалить репозиторий на GitHub, опубликовать заново с чистой историей.
- В списке изменений тысячи файлов → значит, `.gitignore` не был создан вовремя → создайте его до первого коммита и начните заново.
- Откат не вернул проект в рабочее состояние → поломка произошла раньше, чем последняя сохранённая точка → откройте вкладку History, найдите в списке более раннюю точку (не последнюю), нажмите на неё правой кнопкой мыши и выберите Revert changes in commit — это отменит все коммиты после неё и вернёт файлы к тому состоянию.
- Загрузка в GitHub обрывается или зависает → почти всегда виновата папка `node_modules`, которая не должна отправляться → проверьте `.gitignore`.
